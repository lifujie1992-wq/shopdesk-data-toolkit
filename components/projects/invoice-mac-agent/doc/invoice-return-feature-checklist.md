# 抖店消费者开票自动回传 —— 功能点清单与流程说明

> 本文为早期功能规划，表格中的5秒轮询、maxJobs=1及异常转人工等内容不代表当前实现。现行运行逻辑以 [README](../README.md) 为准：每分钟一轮、每批maxJobs=3、每轮maxJobsPerRun=20，同轮缓存店铺列表，失败后整台代理退避5～30分钟；当前没有按单任务失败次数自动转人工的机制。

> 依据：`invoice-return-technical-design.md`、`invoice-return-mac-agent-dev-plan.md`、`invoice-return-shopdesk-reuse.md`。  
> 已按最新需求校准：**最终态 = 全自动提交（含 `save`）**；**关联 = 用 claim 返回的店铺+订单信息在抖店「待开票」列表查记录，且 `payload.orderId` 与记录的 `shop_order_id` 精确相等才算匹配上**。  
> 开发/验证阶段用 dry-run，不真实提交。

---

## 0. 结论先行

方案开发完成后，可以完成您诉求里的：

| 诉求                                 | 能否完成 | 自动化程度               |
| ---------------------------------- | ---- | ------------------- |
| 定时自动连接 VPS 拉取发票文件                  | ✅    | 全自动                 |
| 按 claim 返回的店铺+订单信息在抖店「待开票」列表查记录、关联 | ✅    | 全自动（查到=关联，查不到=关联失败） |
| 匹配成功后自动上传发票文件（`upload_pdf`）        | ✅    | 全自动                 |
| 上传后自动提交开票（`save`）                  | ✅    | 全自动（最终态）            |
| 开发/验证阶段不真实提交                       | ✅    | dry-run 三档开关        |

**最终交付态是全自动闭环**：拉取 → 关联（抖店实时查询）→ 上传 → 提交，无需人工。人工只兜底异常单（关联失败 / 多记录 / 字段不符 / 风控）。

## 1. 功能点清单（分模块、分层次）

分层：**数据层**=存储与状态；**业务层**=解析/匹配/编排逻辑；**接口层**=对外 HTTP 能力；**运维层**=守护、监控、安全。

### 模块 A：云端工作台（部署在 VPS，`replenishment-workbench`）

| 层次  | 功能点                                             | 说明                                                                                         | 业务价值                          |
| --- | ----------------------------------------------- | ------------------------------------------------------------------------------------------ | ----------------------------- |
| 接口层 | 发票上传入口 `POST /api/invoice/ingest`               | 批量接收 PDF，multipart，SHA256 去重                                                               | 客服在任意电脑交发票，无需懂抖店              |
| 业务层 | PDF 文字层解析（pdfjs-dist）                           | 提取发票号码、价税合计、购买方/销售方名称与税号、开票日期                                                              | 把 PDF 变成可匹配的结构化字段             |
| 业务层 | 字段规范化                                           | 名称去后缀、税号大写去空格、金额转分、日期标准化                                                                   | 消除格式差异，避免同公司因写法不同而失配          |
| 业务层 | 云端匹配引擎                                          | 店铺主体 + 抬头 + 税号 + 金额四级匹配，确定「这张发票 → 哪个订单（shop_order_id）+ 哪家店」，产出 matched/unmatched/ambiguous | 给任务提供店铺信息与订单信息                |
| 数据层 | 台账与状态机（SQLite）                                  | 解析、匹配、上传、提交、重试、审计全记录                                                                       | 可追溯、可重试、可对账                   |
| 接口层 | 店铺主体映射 `GET/PUT /api/invoice/shop-mappings`     | 店铺名 → 销售方工商名称/税号                                                                           | 店铺名≠发票销售方全称，映射后云端才能匹配         |
| 接口层 | Mac Agent 注册/鉴权                                 | 注册单台 Mac Token（存哈希）                                                                        | 只允许这台 Mac 领任务，Token 可吊销       |
| 业务层 | 任务队列与租约 `POST /api/invoice/worker/jobs/claim`   | **返回店铺信息 + 订单信息 + 发票下载地址 + leaseToken**；租约 + 一次性 leaseToken 防重复领取                          | 供 Mac 去抖店查询关联；断网任务自动回 pending |
| 接口层 | 结果回传 `POST /api/invoice/worker/jobs/:id/result` | 接收 uploaded/failed/retryable，**必带 leaseToken**，幂等；租约失效返回 409（云端无 submitted）                | 台账与抖店状态同步                     |
| 接口层 | 人工处理界面                                          | 关联失败/多记录/字段不符/failed 单人工兜底                                                                 | 异常单有人处理，不空转                   |

> 说明：`claim` 返回的 `payload.orderId` 与抖店 `shop_order_id` 是同一个值；`shopId` 即店铺标识。关联判定 = 在抖店「待开票」列表查到记录且记录的 `shop_order_id` 与 `payload.orderId` **精确相等**（见模块 C）。

### 模块 B：Mac 回传代理（本机常驻 Node 进程）

| 层次  | 功能点            | 说明                                                | 业务价值                          |
| --- | -------------- | ------------------------------------------------- | ----------------------------- |
| 业务层 | 定时轮询 claim（5s） | 主动 HTTPS 连 VPS 领任务（`maxJobs=1` 串行）                | VPS 无需公网入站端口                  |
| 数据层 | PDF 下载与校验      | 下载签名 URL 的 PDF，校验 SHA256/大小/`%PDF-`               | 保证上传的原件与用户上传一致                |
| 业务层 | 任务编排           | 领任务→下载→关联查询→核对→上传→提交→回传                           | 串行不抢页面；租约 softDeadline 提前让位防重 |
| 业务层 | 错误分类与重试        | 可重试（网络/登录失效）与不可重试（关联失败/字段不符）区分                    | 不无限重试、异常自动转人工                 |
| 业务层 | dry-run 三档开关   | `dry-run`（只查不传）/ `upload-only`（传不提交）/ `auto`（全自动） | 开发验证阶段不真提交，最终切 `auto`         |
| 运维层 | launchd 常驻     | 崩溃/断网自动拉起，日志落盘                                    | 7×24 无人值守                     |
| 安全  | 脱敏回传           | 只回传 jobId/订单号/脱敏 code/msg，不落 Cookie/签名/动态参数       | 不泄露抖店凭证                       |

### 模块 C：店铺工作台开票模块（本机 Electron，复用现有登录态）

| 层次  | 功能点                 | 说明                                                                                                                         | 业务价值                       |
| --- | ------------------- | -------------------------------------------------------------------------------------------------------------------------- | -------------------------- |
| 数据层 | 49 家店登录态复用          | `session.fromPartition('persist:shop-<id>')` Cookie 分区                                                                     | 不重扫码、不复制 Cookie            |
| 业务层 | **订单关联查询**          | 按 claim 的店铺信息定位店铺 → 在抖店「待开票」列表用 `shop_order_id` 查询 → **查到的记录 `shop_order_id` 与 `payload.orderId` 精确相等=关联成功**，不等/查不到=关联失败回传 | 关联以抖店实际记录为准，这是上传/提交的硬门槛    |
| 业务层 | 字段核对                | 查到的记录核对 金额/店铺/状态=待开票（抬头/税号由云端匹配保证）                                                                                         | 上传前最后防线，防错传                |
| 业务层 | 发票文件上传 `upload_pdf` | 页面 fetch + FormData 直连（已实测无需 csrf/动态参数），主进程读 PDF → 页面内 `new File` 上传                                                       | 复用已验证的「页面内发起」，拿 `data.key` |
| 业务层 | 拿 `tos_key`         | `upload_pdf` 响应直接返回 `data.key`（无需网络捕获）                                                                                     | 后续提交用；不落盘签名 URL            |
| 业务层 | **自动提交 `save`**     | 关联+核对通过后，用 `tos_key`+`file_name`+`shop_order_id` 调 `/order/invoice/save`，成功后刷新列表验证                                         | 完成最终开票，闭环无需人工              |

### 模块 D：安全与运维

| 层次 | 功能点        | 说明                                                   | 业务价值       |
| -- | ---------- | ---------------------------------------------------- | ---------- |
| 安全 | 密钥管理       | 云端 Token、agent-bridge token 存 0600 配置文件，不进 Git/DB/日志 | 凭证不泄露      |
| 安全 | dry-run 模式 | 全链路演练（只查/核对/报告，不真传不真提交）                              | 上线前先证明链路正确 |
| 运维 | 登录态健康检查    | 复用 login-health，失效告警/转人工                             | 登录掉了不空转    |
| 运维 | 审计日志       | 解析/匹配/领取/关联/上传/提交全事件留痕                               | 出问题可回溯到每一步 |

## 2. 关键流程节点（拉取 → 关联 → 上传 → 提交）

### 阶段一：拉取

```text
① 用户在云端上传发票 PDF → 云端解析入库 → 云端匹配确定「店铺 + 订单(shop_order_id)」
② Mac 代理 5s 轮询 POST /api/invoice/worker/jobs/claim
   → 返回 { shopId, orderId(shop_order_id), invoiceNumber, amount, fileDownloadUrl, leaseExpiresAt, leaseToken }
③ Mac 下载 PDF 原件 → 校验 SHA256 / 大小 / %PDF-
```

关键节点：

- **A 入库去重**：SHA256 去重，同一张发票不产生第二条记录。
- **B 任务领取+租约**：`BEGIN IMMEDIATE` 原子领取，重复轮询/超时重试不重复领取；每次领取生成一次性 `leaseToken`。
- **C 原件完整性**：下载后校验哈希与魔数，防被换、被截断。

### 阶段二：关联（以抖店后台实时查询为准）

```text
④ 店铺定位：用 claim 的店铺信息（shopId）映射到店铺工作台对应的店铺（登录态）
⑤ 订单查询：打开该店「发票管理 → 给消费者开票 → 待开票」列表，用 payload.orderId 作为 shop_order_id 查询
   ├─ 查到记录且 shop_order_id == payload.orderId（精确相等）→ 关联成功（匹配上）
   ├─ 查到记录但 shop_order_id != payload.orderId → 关联失败（不匹配）
   ├─ 查到 0 条   → 关联失败：回传 failed（订单不在待开票，可能已开票/已取消/单号不对）
   └─ 查到多条   → 关联失败：转人工（理论上同 shop_order_id 唯一，防御性兜底）
⑥ 字段核对：查到的记录核对 金额/店铺/状态=待开票 是否与任务一致（抬头/税号已在云端匹配阶段使用）
   ├─ 一致 → 继续上传
   └─ 不一致 → 回传 failed（业务不匹配，重试无意义）
```

关键节点：

- **D 关联 = 精确匹配**：这是本方案的硬门槛。`payload.orderId` 与抖店 `shop_order_id` 是同一个值，**只有抖店「待开票」列表里查到记录且 `shop_order_id` 与 `payload.orderId` 精确相等，才算匹配上**；不等/查不到绝不上传。定位键只用 `shop_order_id`，不用金额/抬头做模糊匹配。
- **E 店铺信息用于选店**：49 家店各自的待开票列表是隔离的，必须先按 shopId 选对店铺登录态，否则查不到。
- **F 列表快照留证**：查到的记录（title/tax_no/amount/status）随结果回传，写入云端 `invoice_match_candidates` 留审计依据；title/tax_no 是抖店侧读到的值，不用于 Mac 侧强制核对。

### 阶段三：上传 + 提交（最终态全自动，云端状态统一为 uploaded）

```text
⑦ 上传文件：页面 fetch + FormData 直连 `/order/invoice/upload_pdf`（无需动态参数）
   → 响应直接拿 data.key（tos_key）
⑧ 自动提交：关联+核对已通过、且已拿 data.key → 调 /order/invoice/save
   （tos_key + file_name + shop_order_id + invoice_status_type）
   → 成功后刷新 /order/invoice/list 验证状态 → 回传 uploaded
```

关键节点：

- **G 上传**：拿到 `data.key`（`tos_key`），是提交的前置，本身不结束任务。
- **H 提交完成 = uploaded**：`save` 成功 + 列表刷新验证通过，回传 `uploaded`（云端最终成功态，无 `submitted`）。
- **I 全自动提交的触发条件**（全部满足才自动 `save`，否则转人工）：
  1. 关联成功（待开票列表查到唯一记录）；
  2. 字段核对通过（金额/店铺/状态，抬头/税号由云端匹配保证）；
  3. `upload_pdf` 已返回 `data.key`；
  4. 云端匹配唯一（非 ambiguous）；
  5. 记录仍为「待开票」且未被其他任务领取。
- **J 失败回传分类**：关联失败/字段不符 → `failed`（不可重试）；网络/登录/上传超时 → `retryable`；风控/验证码 → `failed` 转人工；回传收到 `409 租约已失效` → 放弃本地结果（已被新领取方接管）。均带脱敏 `code/msg`，不写动态 token/签名 URL。

## 3. dry-run 三档模式（开发验证阶段不真实提交）

| 模式            | 关联查询 | 字段核对  | upload_pdf | save  | 用途                |
| ------------- | ---- | ----- | ---------- | ----- | ----------------- |
| `dry-run`     | ✅ 真查 | ✅ 真核对 | ❌ 不传（报告将传） | ❌ 不提交 | 验证关联与核对逻辑         |
| `upload-only` | ✅    | ✅     | ✅ 真传拿 key  | ❌ 不提交 | 验证上传与 data.key 捕获 |
| `auto`        | ✅    | ✅     | ✅          | ✅ 真提交 | **最终交付态**         |

- 开关放在 Mac 代理配置（`submitMode`），云端不感知；由 `dry-run → upload-only → auto` 逐级放开，每级验收通过再进下一级。
- 最终 `auto` 模式仍受「触发条件 I」约束：任一不满足即转人工，不强行提交。

## 4. 需求澄清结论（已确认）

1. ✅ **`payload.orderId` = 抖店「代开票列表」的「订单信息」列订单号**（即 `/order/invoice/list` 的 `shop_order_id` 字段）。关联判定 = 抖店列表记录的 `shop_order_id` 与 `payload.orderId` 精确相等。
2. ✅ **`payload.shopId` = 店铺工作台 `shops.json` 的 `id`（uuid）**，Mac 代理直接用 `session.fromPartition('persist:shop-'+shopId)` 选登录态，无需二次映射。
3. ✅ **云端已开发完，只开发 Mac 侧**；任务入口 = 前端 `https://erp.xiangduoer.com/#invoice-management` 的「回传核对」用户上传 PDF。
4. ✅ **`save` 失败容错**：先查列表幂等判断——已提交则回 `uploaded`，否则回 `retryable`，错误原因写入 `message` 同步云端。
5. ✅ **全自动提交的风险接受度**：自动 `save` 不可撤回，靠「关联唯一 + 字段核对 + 云端匹配唯一」三道关压错票率；`auto` 模式下仍满足触发条件才提交，否则转人工。

## 附：端到端一句话

> 用户在 `erp.xiangduoer.com/#invoice-management`「回传核对」上传 PDF → 云端入队 → Mac 定时 claim（拿 orderId=抖店订单号、shopId=店铺工作台 id、leaseToken）→ 下载 PDF → 店铺工作台在抖店「待开票」列表查 `shop_order_id` 精确相等=关联成功、核对字段 → 上传拿 `data.key` → 自动 `save` 提交 → 刷新列表验证 → 回传 `uploaded`（带 leaseToken）→ 完成。
