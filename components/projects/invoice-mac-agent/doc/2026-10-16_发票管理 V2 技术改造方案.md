# 发票管理 V2 技术改造方案

> 已实施调整（2026-10-16）：订单主表与发票回传数据统一使用  
> `.local-data/invoice-management-v2.sqlite`。解析台账、原件索引、候选、业务事件、  
> `invoice_upload_jobs`、`invoice_worker`、`invoice_events` 均在此库。  
> 启动时执行一次迁移，完成后不再读取旧 SQLite 库；旧库保留供核对。  
> 原有接口地址保留，统一指向新库。本文后续旧库相关描述为迁移前背景。

## 1. 文档目标

本文档用于设计发票管理 V2 的数据链路、数据库结构、同步接口、状态流转、页面灰度和分阶段实施方案。

V2 采用“新页面、新接口、新主表，旧页面和旧接口保持不动”的方式实施，确保现有 `#invoice-management` 页面继续可用，待 V2 验证完成后再切换入口。

## 2. 业务背景与约束

系统由两台机器组成：

- **Mac 采集机**：登录抖店后台，每天采集消费者待开票数据和平台账单数据；同时负责根据云端任务登录抖店并上传发票。
- **阿里云 VPS**：部署 ERP 工作台，负责接收 Mac 数据、去重、保存历史、维护 ERP 状态、生成 Mac 回传任务，并向页面提供数据。

当前已有数据表：

- `invoice_daily`
- `consumer_invoice`
- `platform_invoice_bill`

当前已有 Mac Worker 任务逻辑：

- `server/invoice-worker-api.mjs`
- `invoice_upload_jobs`
- `invoice_worker`
- `invoice_events`

业务唯一键确认如下：

### 消费者待开票

```text
(shop_id, order_id, sub_order_no)
```

其中 `sub_order_no` 在普通订单中通常为 `NULL`，因此数据库中使用规范化字段：

```text
sub_order_no_key = COALESCE(sub_order_no, '')
```

实际唯一键为：

```text
(shop_id, order_id, sub_order_no_key)
```

### 平台账单

```text
(shop_id, bill_id)
```

### 其他约束

- `stat_date` 只代表数据采集日期，不参与 ERP 业务唯一性。
- 同一个业务记录每天可能重复出现在 Mac 的采集快照中，但 ERP 主表只保留一条当前记录。
- 已开票记录不能从数据库删除，只从“待处理”查询中排除。
- 同一个订单在不同 `shop_id` 下出现时视为数据异常，不应静默合并。
- 所有新建表名统一使用 `invoice_` 前缀。

## 3. V2 总体链路

```text
Mac 每日采集
  ↓
生成 capture_run + 全量快照
  ↓
上传到云端
  ↓
云端校验批次、文件、行数、SHA-256
  ↓
保存每日原始快照
  ↓
按业务唯一键归并到主表
  ↓
新页面查询主表
  ↓
运营上传发票
  ↓
生成 Mac Worker 任务
  ↓
Mac 领取任务并操作抖店
  ↓
Mac 回传成功或失败
  ↓
云端更新 ERP 状态和状态事件
```

数据分为三层：

```text
快照层：每天 Mac 抓到的原始数据
主表层：按业务唯一键归并后的 ERP 当前记录
任务层：等待 Mac 执行的发票上传任务
```

## 5. 云端数据库设计

### 5.1 `invoice_capture_run`：采集批次表

记录每次 Mac 采集批次，不保存订单明细。

```sql
CREATE TABLE invoice_capture_run (
  capture_run_id TEXT PRIMARY KEY,

  stat_date TEXT NOT NULL,
  captured_at TEXT NOT NULL,
  source_machine TEXT NOT NULL DEFAULT 'mac-invoice-agent',

  consumer_row_count INTEGER NOT NULL DEFAULT 0,
  platform_row_count INTEGER NOT NULL DEFAULT 0,
  file_size INTEGER NOT NULL DEFAULT 0,
  file_sha256 TEXT NOT NULL DEFAULT '',

  status TEXT NOT NULL DEFAULT 'created',
  -- created / uploaded / validating /
  -- processing / processed / failed

  received_at TEXT,
  processed_at TEXT,
  error_message TEXT,

  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);

CREATE INDEX idx_invoice_capture_run_date
ON invoice_capture_run(stat_date);

CREATE INDEX idx_invoice_capture_run_status
ON invoice_capture_run(status);
```

用途：

- 防止同一批次重复处理；
- 记录每天实际推送了多少条；
- 校验文件和行数；
- 定位哪一天少推、漏推或处理失败；
- 支持单批次重试。

  created_at TEXT NOT NULL,

    shop_id,

CREATE INDEX idx_invoice_consumer_snapshot_order

### 6.3 回传逻辑改造

当前回传逻辑主要更新发票台账：

```text
invoiceWorkerStore.result()
→ invoiceLedger.markUpload()
```

V2 改为：

```text
invoiceWorkerStore.result()
→ invoiceLedger.markUpload()
→ 更新 invoice_order_consumer 或 invoice_platform_bill
→ 写入 invoice_status_event
```

消费者订单成功：

```text
erp_status = invoiced
```

平台账单成功：

```text
erp_status = invoiced
```


发票删除或解除匹配时，不要直接物理删除正在执行的任务，应将任务标记为：

```text
cancelled
```

## 7. 数据同步接口

新接口使用独立路径，不影响旧接口。

### 7.1 创建采集批次

```http
POST /api/invoice/v2/sync/capture-runs
```

请求：

```json
{
  "captureRunId": "20261016-093000-abc123",
  "statDate": "2026-10-16",
  "capturedAt": "2026-10-16T09:30:00+08:00",
  "consumerRowCount": 500,
  "platformRowCount": 300,
  "fileSize": 865432,
  "fileSha256": "sha256..."
}
```

### 7.2 上传数据文件

```http
POST /api/invoice/v2/sync/capture-runs/{captureRunId}/file
```

文件格式建议：

```text
gzip + JSONL
```

消费者记录：

```json
{
  "businessType": "consumer_order",
  "shopId": "shop-a",
  "shopName": "香朵儿官方旗舰店",
  "orderId": "6953220432659486690",
  "subOrderNo": null,
  "amount": 87.8,
  "invoiceStatus": "待开票"
}
```

平台账单记录：

```json
{
  "businessType": "platform_bill",
  "shopId": "shop-a",
  "shopName": "香朵儿官方旗舰店",
  "billId": "bill-001",
  "billAmountYuan": 1000,
  "billPeriod": "2026-10"
}
```

### 7.3 提交批次处理

```http
POST /api/invoice/v2/sync/capture-runs/{captureRunId}/complete
```

服务端执行：

1. 校验批次是否存在；
2. 校验文件大小；
3. 校验 SHA-256；
4. 校验行数；
5. 写入消费者快照；
6. 写入平台账单快照；
7. 更新消费者主表；
8. 更新平台账单主表；
9. 生成异常记录；
10. 标记批次处理结果。

### 7.4 查询批次状态

```http
GET /api/invoice/v2/sync/capture-runs/{captureRunId}
```

返回：

```json
{
  "captureRunId": "20261016-093000-abc123",
  "status": "processed",
  "consumerReceivedRows": 500,
  "consumerAcceptedRows": 498,
  "platformReceivedRows": 300,
  "platformAcceptedRows": 300,
  "duplicateRows": 2,
  "conflictRows": 0
}
```

### 7.4.1 ERP 已实现的接入约定（2026-10-16）

实现文件：`server/invoice-capture-sync.mjs`；挂载入口：`server/start.mjs`。  
四个同步接口均已实现，沿用 Mac Worker 的独立凭据，不使用浏览器 Cookie：

```http
X-Invoice-Account-Id: <管理员注册的账号 ID>
X-Invoice-Worker-Token: <当前有效的 Mac Agent Token>
```

批次归创建账号所有，其他账号不能上传、提交或查询该批次。

**调用顺序与文件格式**

1. 本地把消费者及平台账单写成 UTF-8 JSONL，再压缩为一个 gzip 文件。
2. 对 gzip 文件本身计算 `fileSize` 和 `fileSha256`。行数是解压后的业务记录数，包含重复行，不包含空行。
3. POST 创建批次，`captureRunId` 为 1～128 位英文字母、数字、短横线或下划线。
4. POST `/{captureRunId}/file`，请求体直接发送 gzip 二进制，建议 `Content-Type: application/gzip`；不是 multipart 表单，也不是 JSON 包装文件。
5. POST `/{captureRunId}/complete`，无需请求体，服务端完成校验及原子入库后同步返回 ACK。
6. 若提交请求超时或结果不明，GET 查询批次；已 `processed` 时不要再上传文件，可重复 complete 取得相同 ACK。

所有成功响应均为 HTTP 200，返回批次信息及统计字段。  
相同 ID、相同清单可重复创建；相同 ID 携带不同文件或行数等清单内容返回 409。  
已处理批次不可覆盖文件。未处理批次可重新上传同一清单对应的文件后重试。

**大小限制与失败处理**

- gzip 文件最大 256 MiB；解压后最大 1 GiB；单行最大 1 MiB；每批最多 100 万条业务记录。
- 上传采用流式落盘和 SHA-256 校验，先写临时文件，校验通过后才原子改名。
- complete 再次核对磁盘文件的大小和 SHA-256，并流式解析 JSONL，不把整个文件作为一个 JSON 数组读入内存。
- gzip 损坏、JSON 无效、必要业务键缺失或金额无效、行数不符，均标记 `failed`，不会修改主表。
- 所有快照、主表更新及最终 `processed` 状态同一事务提交；数据库错误会整批回滚。
- 同一批次在上传或处理期间的并发写入返回 409。服务重启时中断的 `validating` / `processing` 批次标记 `failed`，可重试。
- 典型错误码：400 数据或校验错误，401 凭据错误，404 批次不存在或不属于当前账号，409 状态或清单冲突，413 超限，405 方法不支持。
- 对外部署时，反向代理的上传大小和处理超时也需允许对应文件规模；ERP 本地限制不能代替反向代理配置。

**入库口径**

- 订单号、店铺 ID、子订单号、账单号均使用 JSON 字符串；尤其不能用数字发送 19 位订单号。
- 无子订单时传 `null` 或空字符串，归一为 `sub_order_no_key = ''`。
- 平台金额接收 `billAmountYuan`（兼容 `amount`），未结金额接收 `unpayAmount`（兼容 `unpaidAmount`），单位均为元。
- `consumerAcceptedRows` / `platformAcceptedRows` 为实际保存的唯一快照行数，包含已记录冲突的业务键；`duplicateRows` 是同批相同业务键的额外行数。
- `conflictRows` 为当前批次影响主表的冲突业务键数，明细保存在 `invoice_capture_anomaly`；`staleRows` 为仅保留快照、未覆盖更新主表的过期记录数。
- 同批一个业务键存在多个不同金额、抬头或税号时保留首条快照，并将差异完整记入异常表，避免按文件顺序任意覆盖。
- 已进入回传流程的订单发生采集冲突时，保留原业务字段、发票绑定和处理状态，记录异常；不会把已回传状态降级为待处理。
- 其他冲突数据标为 `data_conflict`，不参与自动匹配及待开票导出；V2 显示“信息待核对”。
- 旧批次晚到仍保留其快照，但不能覆盖同一业务键较新的采集事实，也不增加缺失次数。
- 每批均表示两类数据的完整全量，不能把分页、失败店铺的残缺数据或增量数据当成完整批次提交。
- 仅更新的完整批次推进缺失计数，默认连续 3 批未出现才把未开票记录标为 `source_missing`；不据此判断已开票，也不覆盖回传中、已回传等处理状态。
- 数据重新出现时清零缺失次数，`source_missing` 恢复为 `pending_invoice`。

**运行时数据源切换**

在首个 Mac API 批次成功前，保留当前旧数仓导入的兼容方式。  
首个批次成功后，V2 页面、统计和趋势自动使用同步库，不再从旧数仓导入覆盖主表。  
新增的 `invoice_capture_stage` 仅为可重建的校验暂存；`invoice_capture_anomaly` 保留批次异常。  
两表与扩展后的 `invoice_capture_run` 都在 `invoice-management-v2.sqlite` 中，前端不新增采集批次 Tab。
