## 3. 接口契约（真实实现 + shopResults 新增）

### 3.1 端点与鉴权

前缀固定 `/api/invoice/v2/sync/`，四步流程不变：

| 方法   | 路径                                                | 作用              |
| ---- | ------------------------------------------------- | --------------- |
| POST | `/api/invoice/v2/sync/capture-runs`               | 创建批次（清单，≤64 KB） |
| POST | `/api/invoice/v2/sync/capture-runs/{id}/file`     | 上传 gzip（流式）     |
| POST | `/api/invoice/v2/sync/capture-runs/{id}/complete` | 校验并原子入库，返回 ACK  |
| GET  | `/api/invoice/v2/sync/capture-runs/{id}`          | 查询批次状态          |

- 鉴权头：`X-Invoice-Account-Id` + `X-Invoice-Worker-Token`（**即现有凭据**）；无效 → `401`；
- 批次按创建账号隔离，业务数据写入共享 V2 主表；
- 方法不匹配 → `405`；路径不存在 → `404`；错误体统一 `{ error }`。

### 3.2 创建批次入参

**基础字段**（服务端已实现校验）：

| 字段                 | 类型/规则                        |
| ------------------ | ---------------------------- |
| `captureRunId`     | `^[A-Za-z0-9_-]{1,128}$`     |
| `statDate`         | `YYYY-MM-DD`，合法日历日           |
| `capturedAt`       | 字符串，必须以 `Z` 或 `±HH:MM` 结尾    |
| `consumerRowCount` | 非负安全整数                       |
| `platformRowCount` | 非负安全整数                       |
| `fileSize`         | 整数；**必须 `> 0`** 且 `≤ 256 MB` |
| `fileSha256`       | 64 位十六进制（**对 gzip 文件本身**）    |

行数合计上限 **1,000,000**（超 → `413`）。

**新增字段 `shopResults`**（**必填**，数组，逐「店铺 × 业务类型」报告；来自已上线实现的真实校验）：

| 字段             | 类型             | 说明                                            |
| -------------- | -------------- | --------------------------------------------- |
| `shopId`       | string         | 店铺 ID，必须字符串                                   |
| `businessType` | string         | `consumer_order` 消费者申请 / `platform_bill` 平台账单 |
| `status`       | string         | `success` / `failed`                          |
| `isComplete`   | boolean        | 是否完成该店该业务**全部采集（含全部分页）**                      |
| `rowCount`     | integer / null | 成功 = 本次上传的该店该业务明细行数；失败 = **必须 `null`**        |
| `errorCode`    | string / null  | 失败原因编码（≤64 字符），成功 = **必须 `null`**             |
| `errorMessage` | string / null  | 失败说明（≤1000 字符），成功 = **必须 `null`**             |

服务端强校验（违反即 `400`）：

- **必填**：`1 ~ 2000` 条（`maxShopResults = 2000`）；本仓库 54 店 × 2 业务 = 108 条，规模安全（create 清单上限 64 KB）；
- `success` 项：`isComplete` 必须 `true`、`rowCount` 必须为非负安全整数（≤ 100 万）、`errorCode`/`errorMessage` **必须为 `null`**（给值报错）；
- `failed` 项：`isComplete` 必须 `false`、`rowCount` **必须为 `null`**、`errorCode`/`errorMessage` 必须为**非空**字符串；
- 同一批次中，**每个 `shopId + businessType` 只能报告一次**；
- 失败原因编码约定：`LOGIN_EXPIRED` / `PAGE_TIMEOUT` / `PARSE_FAILED` / `PAGINATION_FAILED` / `OTHER`；
- 即使前几页拿到了数据，只要**没有完整抓完**，本次按失败报告，**不上传该店该业务的部分明细**；
- **幂等一致性（重要）**：同批次重试时 `shopResults` 必须与首次**逐字节一致**，否则 `409 批次 ID 已被不同店铺采集结果使用`（manifest 原样保存、重放原样携带，见 §6）。

行数对账（complete 阶段，双重校验，违反即 `400`）：

1. **总行数**：解压后 consumer 总行数 == `consumerRowCount`，platform 总行数 == `platformRowCount`；
2. **逐店逐业务**：每个 `success` 单元的实际明细行数 == 该项 `rowCount`（报错文案：`店铺 X 的 Y 明细行数与 shopResults 不一致`）。

其他约定：

- `rowCount` 只统计**上传文件里的业务明细行**，不把 `shopResults` 算进去；**重复明细行也计入**；
- 整批成功结果全为 0 条时，上传一个**合法空 JSONL 的 gzip 文件**（非零字节）。

**幂等规则**：`captureRunId` 已存在且 `accountId + statDate + capturedAt + 两个行数 + fileSize + fileSha256` **全部相同** → `200` 复用；任一不同 → `409`。  
→ **重试必须复用第一次的 `capturedAt`**，不能重取当前时间。

### 3.3 上传文件（`/file`）

- body = **gzip 二进制**（`Content-Type: application/gzip`）；服务端边收边算大小与 SHA-256；
- 与清单不符 → `400`；超清单大小 → `413`；`processed` 时 → `409`；成功后 `status=uploaded`。

### 3.4 提交批次（`/complete`）

- 前置 `uploaded`；`processed` 重复调用幂等返回 `200`；
- 服务端 gunzip → 逐行校验：每行为对象、`businessType ∈ {consumer_order, platform_bill}`、行内 `statDate`（若有）必须等于批次 `statDate`；
- **总行数对账**：consumer 解压行数 == `consumerRowCount`；platform 解压行数 == `platformRowCount`；
- **逐店对账**：每个 `success` 的 `shopResults` 项，该店该业务的实际明细行数 == 其 `rowCount`（否则 `400 店铺 X 的 Y 明细行数与 shopResults 不一致`）；
- 校验通过后**同一事务**写「快照表 + 主表 + 最终 ACK」；失败置 `status=failed`，可重传后再次 `complete`。

### 3.5 状态字段（`view`）

```json
{"captureRunId":"...","statDate":"2026-10-16","capturedAt":"...","status":"processed",
 "consumerRowCount":0,"platformRowCount":0,
 "consumerReceivedRows":0,"consumerAcceptedRows":0,
 "platformReceivedRows":0,"platformAcceptedRows":0,
 "duplicateRows":0,"conflictRows":0,"staleRows":0,
 "fileSize":0,"fileSha256":"...","error":null,"receivedAt":null,"processedAt":null}
```

`status`：`created → validating → uploaded → validating → processing → processed`，异常为 `failed`。

### 3.6 入库口径（决定 Mac 侧怎么造数据）

主表主键即业务唯一键：`invoice_order_consumer(shop_id, order_id, sub_order_no_key)`、`invoice_platform_bill(shop_id, bill_id)`。

- **字段结构固定**：consumer 只认 `shop_name, registration_id, title, tax_no, invoice_type, amount, apply_time, order_status, source_invoice_status, deadline_time, deadline_text`；platform 只认 `shop_name, credit_code, scene, scene_text, bill_amount_yuan, bill_amount_raw, order_count, bill_period, create_time, corp_title, corp_tax_no, is_frozen, pay_status, unpay_amount`。多余字段丢弃；
- **状态保护**：`pending_mac_upload / uploading / upload_failed / invoiced / handled / marked` 不被采集覆盖；
- **冲突判定**：consumer 比 `amount / title / tax_no`，platform 比 `bill_amount_yuan / bill_period / corp_title / corp_tax_no`；不一致 → `erp_status='data_conflict'` + 写异常表；
- **缺失计数**（已上线口径）：
  - **水位规则**：缺失计数只与**同店铺、同业务**最近一次「完整成功采集」(`success + isComplete=1` 且批次 `processed`) 比较；其他店铺的新批次、失败批次**不构成水位**；
  - `success + isComplete + rowCount>0`：出现的记录**清零**缺失次数，未出现的历史记&#x5F55;**+1**；
  - `success + isComplete + rowCount=0`：该店该业务历史记录全部 **+1**；连续 **3 次完整成功**都未出现，才将仍待开票的标 `source_missing`（Mac 须确认登录正常、页面加载完成、筛选正确、明确识别"暂无数据"，才能上报这种情况）；
  - `failed`：缺失次数**既不加也不清零**（保留历史）；
  - 未报告：缺失次数不变；
- `source_invoice_status` 原样存来源状态。

## 4. 采集口径（与 `invoice.py` 对齐，去掉待红冲）

### 4.1 采集动作

每个店铺（`platform == '抖店'`）依次：

1. `GET /api/ecomfinance/subject/list` → 主体列表（含 `HasPendingPlatformInvoiceBill`），用于判断是否拉平台账单；2026-10-19 字段设计拟在对应账单行直接附带主体公司名称、信用代码，不生成独立主体记录，详见补充文档；

3. ~~`invoice_status_desc=wait_red` 待红冲~~ → **本次不采集**（用户已确认）；

### 4.2 Cookie 与店铺来源（Node 等价实现）

- 店铺表：`~/Library/Application Support/shopdesk/shops.json` → `[{id, name, platform}]`；

运行时：现有 launchd 用 Node 24.20.0，`node:sqlite` 可用。

### 5.1 采集结果模型（容错核心）

**容错原则（用户已确认）：单店失败 → 记 `error`，继续跑其他店**——与 Python 原行为一致；由 `shopResults` 把失败如实上报云端，云端据此保留历史、不动缺失计数。

采集按「**店铺 × 业务类型**」两个独立单元推进，每个单元产出一条 `shopResults`：

| 单元                        | 判定                                                                                                                                       |
| ------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `shopId + consumer_order` | 待开票列表**全部分页**抓完 → `success/isComplete=true, rowCount=实际行数(可 0)`；任一分页失败/超时/解析失败 → `failed/isComplete=false, rowCount=null, errorCode=对应码` |
| `shopId + platform_bill`  | 所有 `has_pending_platform` 主体的账单**全部**抓完 → `success`；任一失败 → `failed`（同上）                                                                  |

规则：

- **失败单元的部分明细一律丢弃，不进 JSONL**（即使前几页已拿到数据）；
- 同一家店「消费者成功、平台失败」分别报告、分别处理；
- 采集失败的店铺**不影响**其他店铺继续采集与上传（容错继续）；
- 全部单元都失败时：仍可上传一个**空 JSONL gzip**并附带全 `failed` 的 `shopResults`（缺失计数不变，仅留审计痕迹）；该行为作为配置项，默认**上传**；
- `--dry-run` 不上传，直接输出本地结果（含 `shopResults`）供查看。

## 6. 打包与批次

- **`statDate`**：Mac 本地 `Asia/Shanghai` 日期 `YYYY-MM-DD`；
- **`capturedAt`**：采集完成时刻完整 ISO（带 `Z`）；
- **`captureRunId`**：`mac-{YYYYMMDD}-{HHMMSS}-{contentHash8}`
  - `contentHash8` = `sha256(规范化 JSONL 文本)` 前 8 位；行按 `(businessType, shopId, orderId|billId)` **稳定排序**、键序固定，保证同内容同 ID；
  - 满足 `^[A-Za-z0-9_-]{1,128}$`；内容不变 → 同 ID（重试幂等）；内容变 → 新 ID（避开 `409`）；
- **`fileSize` / `fileSha256`**：对 **gzip 文件本身**计算（`fileSize` 必须 `>0`，空批次用合法空 JSONL 的 gzip ≈ 20 B）；
- **行数**：`consumerRowCount = 待开票条数`；`platformRowCount = 平台账单条数`；解压后逐行统计，空行不计；
- **manifest 持久化**：`~/.local/share/invoice-mac-agent/capture/<statDate>-manifest.json`  
  存 `{captureRunId, statDate, capturedAt, consumerRowCount, platformRowCount, fileSize, fileSha256, shopResults, gzipPath, status}`。  
  `--resume`：若存在当天未完成（无 `processed`）的 manifest 且 gzip 与 `fileSha256` 一致 → **原样重放** `create → file → complete`（复用同一 `capturedAt` **并原样携带同一份 `shopResults`** —— 服务端对 shopResults 也做幂等比对，不一致会 `409 批次 ID 已被不同店铺采集结果使用`）。

## 7. 上传流程

```text
① prepare  manifest：算 id / size / sha256 / 行数 / shopResults
② create   POST capture-runs            body 含 captureRunId..fileSha256 + shopResults
③ file     POST capture-runs/{id}/file  body=gzip, Content-Type: application/gzip
④ complete POST capture-runs/{id}/complete → status=processed，返回各计数 ACK
⑤ 结果不明 → GET capture-runs/{id} 查状态
```

错误处理：

| 情形                           | 处理                                                  |
| ---------------------------- | --------------------------------------------------- |
| `401 / 403`                  | **致命**，停止并告警                                        |
| `409`（清单冲突 / 正处理）            | 先 `GET` 查；`processed` 视为成功，否则上报人工                   |
| `409`（`/file` 已 processed）   | 视为已完成，跳过                                            |
| `413`（超行数/超大小）               | 致命，不入库，告警                                           |
| `400`（字段/金额/哈希不符）            | 致命，修采集或打包逻辑                                         |
| 网络 / `408 / 425 / 429 / 5xx` | 指数退避重试（`withRetry`，上限 30s，≤5 次）                     |
| 超时后重试                        | **不重传 `/file`**，先 `GET` 查；`uploaded` 则直接 `complete` |

## 10. 风险与应对

| 风险                                  | 影响           | 应对                                             |
| ----------------------------------- | ------------ | ---------------------------------------------- |
| 逐店行数对账失败（`rowCount` 与实际明细不符）        | `400` 整批失败   | 打包层按 (shopId × businessType) 精确计数，失败单元明细丢弃后再计数 |
| 重试时 `capturedAt` 或 `shopResults` 变了 | `409` 失败     | manifest 持久化 + `--resume` 原样重放（两者都参与幂等比对）      |
| 金额含 `￥/,` 未清洗                       | 整批 `400`     | 归一化层统一 `toNumber`                              |
| 19 位订单号精度                           | `400` / 数据错乱 | 一律字符串                                          |
| 并发两次采集抢 cookie 锁                    | 采集失败         | `capture.lock`                                 |
| 平台账单只取第 1 页（沿用原逻辑）                  | 可能漏账单        | 与 Python 一致；如需全量单列需求                           |
| 与 xdr 双跑口径差异                        | 对账不齐         | 阶段 6 并行对账，先不切                                  |
