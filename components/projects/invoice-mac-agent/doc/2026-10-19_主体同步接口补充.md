# 发票 V2：订单、账单主体字段接口补充

日期：2026-10-19。状态：**Mac 已实现，云端已部署，已按日常采集链路完成全量上传、入库及主体字段核对（见第 8 节）**。本文是两端当前字段契约。

## 1. 本次变更

在原有 `consumer_order` 和 `platform_bill` 的每条 JSONL 记录内直接携带该订单或账单对应的公司名称、信用代码：

```json
{"companyName":"该条记录对应的开票主体公司全称","creditCode":"该主体的统一社会信用代码"}
```

- `businessType` 仍只有 `consumer_order`、`platform_bill`。
- 不上传独立主体资料行，不增加主体表、主体专用接口、主体计数或主体 ACK。
- `platform_bill.creditCode` 原本已有，继续使用；该类记录只需增加 `companyName`。`consumer_order` 增加两个字段。
- 公司名称和信用代码由 Mac 按下述业务规则成对传入，云端直接保存，不根据税号反查名称，也不依赖云端维护店铺与公司的映射。
- 用户已确认：消费者待开票记录统一使用采集时当前店铺的最新主体；平台账单使用各自查询主体。该规则已在采集、字段填充及打包校验中实现。

## 2. 字段定义与归属

| JSONL 字段      | 类型            | 消费者订单 | 平台账单   | 含义                                     |
| ------------- | ------------- | ----- | ------ | -------------------------------------- |
| `companyName` | string / null | 新增    | 新增     | 该条订单或账单对应的商家开票主体公司全称                   |
| `creditCode`  | string / null | 新增    | 保留已有字段 | 与同条 `companyName` 对应的统一社会信用代码，始终按字符串处理 |

新格式记录同时包含这两个键。已确定主体时，两项都为非空字符串；尚不能确定时，两项都为 null。不使用空字符串、0、店铺名称或其他占位值表达未知。

字段值必须来自同一次主体选择，不能把一个主体的名称和另一个主体的信用代码拼在一起。一条记录只携带一组主体字段。消费者按用户确认的规则统一使用店铺最新主体；平台账单保留各自当前或历史查询主体。

以下信息含义保持原样：

| 记录 / 字段                               | 含义               |
| ------------------------------------- | ---------------- |
| `consumer_order.title / taxNo`        | 购买方发票抬头、购买方税号    |
| `platform_bill.corpTitle / corpTaxNo` | 平台收票方名称、税号       |
| 两类记录的 `companyName / creditCode`      | 商家开票主体名称、信用代码    |
| `shopId / shopName`                   | 店铺标识与店铺名称，不是公司主体 |

### 2.1 平台账单的取值依据

现有采集按每个主体的 `CreditCode` 查询平台账单：

```text
GET /api/ecomfinance/subject/list
  → 对主体调用 /api/ecomfinance/uninvoicebill/getPage?credit_code=该主体CreditCode
```

该次查询返回的每条账单，直接填写同一主体对象的 `CompanyName → companyName`、`CreditCode → creditCode`。历史主体下的账单使用历史主体，不覆盖成当前主体。该对应关系表示账单所属开票主体，不表示待开票账单已经完成实际开票。

若来源信息不足以形成完整的名称/信用代码对，不得用其他主体补齐。具名主体下存在真实账单但公司名称或信用代码不完整时，该店平台业务失败并丢弃该单元部分明细，避免上传半组字段。平台原有空主体账单确认、分页完整性等校验保留。

### 2.2 消费者订单：统一匹配店铺最新主体

用户已明确授权使用当前店铺最新主体匹配消费者待开票记录。这是业务指定的关联规则，不表示消费者发票接口直接返回了实际历史开票主体。

实现步骤：

1. 每店只查询一次 `/api/ecomfinance/subject/list`，与平台采集共用原始主体列表。
2. 取列表中唯一 `IsNewSubject` 为 true 的主体。兼容来源布尔表示 `true`、`1`、`"1"`、`"true"`；不按列表第一项、历史到期时间或待平台开票标志选择。
3. 该主体不能被标记为已注销，且 `CompanyName`、`CreditCode` 都必须是非空字符串。
4. 在该店本次 `wait_blue` 全部分页的每条记录中，直接填入该主体的 `companyName`、`creditCode`。店铺之间独立选择，不能共用上一店结果。
5. 主体接口失败、缺少唯一最新标志、多个最新标志、最新主体已注销或名称/信用代码不完整时，消费者记录两项同时传 null，并记录 `capture_consumer_subject_unavailable` 日志。继续采集消费者订单，保留原有消费者/平台业务失败隔离；不另建业务单元。

无法选择最新主体时：

```json
{"companyName":null,"creditCode":null}
```

已核对「香朵儿官方旗舰店」来源最新标志对应：`广州鹿溪服饰有限公司` / `91440106MAK442EN1L`。按本规则，该店本次所有消费者待开票记录都使用这一对字段；其他店铺取各自来源最新主体。云端直接接收逐条传入的结果，不再选择或反查主体。

## 4. 四个现有同步接口

鉴权、端点和 create → file → complete → GET 恢复流程保持现有契约。

| 方法   | 路径                                                | 本次要求                                               |
| ---- | ------------------------------------------------- | -------------------------------------------------- |
| POST | `/api/invoice/v2/sync/capture-runs`               | 创建清单字段不变，继续使用两类记录行数和原有 `shopResults`               |
| POST | `/api/invoice/v2/sync/capture-runs/{id}/file`     | gzip JSONL 的两类原有记录接受并保留 `companyName`、`creditCode` |
| POST | `/api/invoice/v2/sync/capture-runs/{id}/complete` | 校验两个字段，随对应订单或账单原子入库，返回原有 ACK                       |
| GET  | `/api/invoice/v2/sync/capture-runs/{id}`          | 批次状态和计数结构不变                                        |

具体约束：

- `consumerRowCount`、`platformRowCount` 及每店每业务 `rowCount` 仍只计算原有订单和账单行数；添加两个字段不增加记录数。
- `shopResults[].businessType` 仍只有原有两个值；不新增业务单元。
- 不增加 `subjectRowCount`、`subjectReceivedRows`、`subjectAcceptedRows`；ACK 对账等式仍为原有两类 acceptedRows 加 duplicateRows 等于原有两类 rowCount 之和。
- 创建清单不携带每条订单的主体信息；主体字段随明细文件上传。现有清单、压缩文件和解压大小等限制继续适用。
- 含新增字段的完整 JSONL 重新计算 gzip、`fileSize`、`fileSha256` 和内容哈希。同批重试和 `--resume` 仍原样复用持久化文件，不在恢复时重新匹配或改字段。

## 5. 云端校验、存储与兼容

### 5.1 新旧格式校验

1. 新格式记录包含两个键：两项均为非空字符串或均为 null。拒绝类型错误、空白字符串、只填写一项或名称/信用代码一项为 null 而另一项非空，返回现有格式的 400 错误。
2. 旧消费者记录可完全缺少两个键；旧平台记录可保留已有 `creditCode` 而缺少 `companyName`。这两种情况继续接受，不强制旧客户端补齐。
3. 明确区分旧平台记录缺少 `companyName` 与新格式显式传 `companyName:null`：后者必须满足上述成对校验。
4. 云端直接使用传入公司全称和信用代码。不能用购买方 `taxNo`、收票方 `corpTaxNo` 或店铺当前主体补全。

### 5.2 数据库字段

在现有快照和主表上补充列，无需新增主体业务表：

| 现有数据表           | 变更                                                   |
| --------------- | ---------------------------------------------------- |
| 消费者订单快照、消费者订单主表 | 增加可空 `company_name TEXT`、`credit_code TEXT`          |
| 平台账单快照、平台账单主表   | 增加可空 `company_name TEXT`；已有 `credit_code` 继续使用，勿重复建列 |

JSONL 的驼峰字段映射为上述列。主体作为该记录的属性，原有业务唯一键保持不变：消费者 `(shop_id, order_id, sub_order_no_key)`，平台 `(shop_id, bill_id)`。不将 `companyName` 或 `creditCode` 拼入新的唯一键，避免补齐主体时重复建单。

### 5.3 更新规则

- 快照按原始请求保存字段；主表与原有订单、账单在同一事务更新。来源时间水位和旧批次不覆盖新数据的规则继续生效。
- 新记录尚无已确认主体时，可保存两个 null；历史旧记录也允许主体未知。
- 旧请求缺字段，或新请求两个字段均为 null，均不表示清除已有已确认主体。不得把已经保存的完整主体对擦掉。
- 已有主体未知、新请求首次提供完整主体对时，同时补齐名称和信用代码，不改变人工处理、已开票等原有业务状态。
- 消费者待开票主表中的这两个字段表示采集时店铺最新主体。较新的采集提供完整主体对时，可按本业务规则成对刷新；店铺切换最新主体可能导致同一待开票记录的字段变化，这一变化本身不构成金额/购买方抬头等财务冲突。已经开票、正在回传或人工处理等受保护状态继续遵守原有状态保护，不能用待开票采集覆盖已开具发票的实际销售方关系。
- 平台账单的字段表示账单查询主体，不能随店铺最新主体变化而替换。若同一账单的新信用代码与已存值不同，走现有数据冲突/异常核对机制，不拼接或静默改归属；名称差异也保留待核对。
- 兼容旧平台记录时，只能在信用代码一致的前提下沿用已有名称；若信用代码变化却没有提供对应名称，不得与旧名称拼成新主体对，应报告归属差异待核对。
- 来源缺失计数、采集失败隔离、金额校验、重复行计数继续按原有两类业务执行，不为主体字段单独新增计数或业务状态。

### 5.4 云端读取接口

现有消费者和平台账单的 list/detail/export 等读取接口，在各条记录直接返回 `companyName`、`creditCode`。历史未知值为 null；旧平台记录有信用代码但尚无名称时如实返回，不反查或伪造名称。

名称与信用代码要贯穿上传白名单、快照、主表、查询字段、响应序列化和导出，避免上传后因固定字段列表而丢失。

## 6. 给云端 AI 的实施清单

1. 在现有 `invoice-capture-sync.mjs` 的两类 JSONL 行字段中接收 `companyName`、`creditCode`，按本文件兼容并校验新旧格式。
2. 在 `invoice-v2-store.mjs` 或对应迁移中，给消费者快照/主表新增两个可空列，给平台快照/主表补充公司名称列，沿用平台已有信用代码列。
3. 保存时按同一条订单/账单成对处理主体字段，落实未知不擦除、消费者待开票随较新采集更新最新主体、平台账单归属差异进入异常核对等规则。
4. 原有批次接口字段、businessType 枚举、业务唯一键、`shopResults` 和 ACK 计数保持两类业务结构。
5. 现有 list/detail/export 返回每条记录自身的公司名称和信用代码，不建立额外店铺主体映射，也不从主体目录猜消费者归属。
6. 增加验证：消费者全部分页使用本店唯一最新主体、平台历史账单仍用历史主体、多店不串用主体、主体异常时消费者双 null、旧格式兼容、半组字段拒绝、状态保护、原行数和 ACK 不变。
