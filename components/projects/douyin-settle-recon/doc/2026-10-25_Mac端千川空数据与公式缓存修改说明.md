# Mac 端修改说明：千川无数据兼容、费用公式缓存与上传前校验

日期：2026-10-25  
适用范围：Mac 端生成店铺月度 Excel，并通过 `POST /api/douyin-recon/v1/reports` 上传的流程。

## 1. 修改目标与已确认的问题

千川当月没有发生额是正常业务情况，需要正常生成账单并同步费用汇总。必须区分“成功获取、确认为空”和“没有成功取得数据”。

已读取以下 8 家线上上传原件，发现同样的问题：千川页存在，但诊断扫描的前 10000 行没有找到公式引用的“总计”行；「核对汇总」D44、D45 均有公式，但保存结果为空。仅打开 Excel 重算，不能补出缺失的源总计数据。

| 店铺 ID     | 店铺名称               |
| --------- | ------------------ |
| 211869289 | 财气满满服饰店            |
| 211900045 | FASHIONMOMENT服饰旗舰店 |
| 230850008 | ME时尚女装             |
| 254175611 | 温裳服饰               |
| 266314577 | DLIN DLING服饰店      |
| 299840356 | 鹿小鸭女装旗舰店           |
| 306044479 | QUEEN GLOW服装专卖店    |
| 306050085 | QUEEN GLOW服饰       |

这只能证明源总计和计算结果缺失，不能据此认定这 8 家实际费用均为零。Mac 端需根据原平台获取结果判定。

## 2. 获取结果必须分成三种状态

以下状态用于 Mac 内部处理和本地日志，不新增到现有上传 metadata；云端当前会拒绝未约定的额外字段。

| 内部状态            | 判断条件                                  | 处理方式                             |
| --------------- | ------------------------------------- | -------------------------------- |
| `success_data`  | 获取成功，店铺、月份正确，源文件/响应有效，数据完整            | 按实际金额生成总计和汇总结果                   |
| `success_empty` | 获取成功，平台明确返回当月无发生；确认不是分页遗漏、筛选错误或下载失败   | 按当月零发生处理，生成数值为零的发生额总计和费用结果       |
| `failed`        | 超时、无权限、下载失败、响应无法解析、结果未完整取得，或无法确认空数据原因 | 保留具体错误并重试，不把本次产物标记为正常完成，不补零伪装为成功 |

文件不存在、文件字节数为零、解析后零行、只有模板表头，都不能单独作为 `success_empty` 的依据。日志应保留店铺 ID、月份、结果状态、数据条数和脱敏原因，便于确认“真实无发生”与“获取失败”。

## 3. 兼容正常无数据：仍生成可被公式引用的总计行

### 3.1 有数据

沿用源数据的有效“总计”行，要求 A 列精确匹配“总计”，且只有一条。当前模板依赖的列如下：

| 列 | 表头       | 用途           |
| - | -------- | ------------ |
| C | 非赠款消耗(元) | D44 取该列金额的负数 |
| D | 赠款消耗(元)  | D45 的减项      |
| I | 总存入(元)   | D45 的被减项     |

先按表头验证布局，再读取对应列，避免源文件改版后错取列。有明细但无总计时，可在确认数据完整、字段口径一致后从明细生成唯一的月度总计；已有总计时不要再次累计它。金额使用十进制计算，沿用原模板精度和符号规则。

### 3.2 成功且确认为空

保留「千川账户」页的既有表头和布局，在 A:N 数据区域内的合适位置生成一条“总计”行。使用现有位置或空白行，不覆盖 Q:R 的余额区域。

| A 列 | C 列 | D 列 | I 列 |
| --- | --: | --: | --: |
| 总计  |   0 |   0 |   0 |

以上零值必须是 Excel 数值，不是文本 `"0"`、空字符串或错误值。其他当月发生额字段如需被模板引用，也按已确认的零发生额填写。

**无发生额不代表账户余额为零。** L:N 的余额字段、Q4/R4 的独立余额以及核对汇总期初/期末余额，仍取真实余额或按现有云端规则结转；未知余额保留缺失状态，不批量补零。费用页同步成功也不要求余额异常一并消失。

## 4. D44、D45 的处理规则

以下地址对应当前模板。定位时同时检查 B/C 列账户和费用名称，模板变化时按名称定位，不能只硬编码行号。

### 4.1 D44：千川账户／非赠款消耗

保留原公式：

```excel
=-INDEX(千川账户!C:C,MATCH("总计",千川账户!A:A,0))
```

Mac 端对应计算：`D44 = -总计行的「非赠款消耗(元)」`。

- 有数据：使用源金额的负数，不重复取负，不额外改变舍入规则。
- 确认无发生：结果为数值 `0`。
- 源金额未知：报出缺失原因，不能用 `0` 替代。

### 4.2 D45：千川账户／巨量千川充值

保留原公式及当前业务口径：

```excel
=IFERROR(INDEX(千川账户!I:I,MATCH("总计",千川账户!A:A,0))-INDEX(千川账户!D:D,MATCH("总计",千川账户!A:A,0)),"")
```

Mac 端对应计算：`D45 = 总计行的「总存入(元)」－总计行的「赠款消耗(元)」`。

- 有数据：按上述原公式计算，不在本次修改中变更充值口径。
- 确认无发生：`0 - 0 = 0`，保存数值 `0`。
- 缺少总计或必需金额：原公式的 `IFERROR(...,"")` 会隐藏错误并返回空字符串。Mac 应在生成阶段发现该问题，不能把空字符串当作有效费用结果，也不要改成无条件 `IFERROR(...,0)`。

D44 和 D45 必须同时修复。云端遇到第一个无效费用就会阻断该店费用区块；只修 D44 后仍可能在 D45 失败。

### 4.3 关联结果

「核对汇总」N6 当前公式为：

```excel
=SUMIF(B:D,L6,D:D)
```

它汇总千川账户对应的费用行。保留公式，在 D44、D45 及其他千川费用行全部就绪后更新其计算结果；当全部千川费用发生额确认为零时，N6 的结果也应为数值 `0`。不要绕过未知费用直接把 N6 写为零。

## 5. 公式与结果缓存必须同时可用

云端读取 Excel 已保存的结果，不执行任意 Excel 公式。公式文本存在、设置“打开时自动重算”，都不能代替已保存的有效结果。

实现可选路径：

1. 保留现有公式，由 Mac 程序计算相同口径的结果，并通过导出工具支持的方式保存数值缓存。
2. 生成完整源数据和公式后，通过能执行这些公式的计算引擎重算、保存，再检查最终文件。

如果使用 openpyxl，它本身不执行公式计算；`data_only=True` 只读取已有缓存。XlsxWriter 支持通过 `write_formula()` / `write_array_formula()` 的结果参数写入已计算值，但不会自动计算真实结果，不可依赖默认缓存零值。参考：[openpyxl 公式说明](https://openpyxl.readthedocs.io/en/stable/simple_formulae.html)、[XlsxWriter 公式结果说明](https://xlsxwriter.readthedocs.io/working_with_formulas.html#formula-results)。不要求仅为本次修改更换现有导出工具。

最终文件要求：

- 保留原公式、样式、数字格式和必要的数组公式元数据。
- D44、D45 的结果缓存为真实数字，零发生时为数值 `0`，不保存成字符串类型的公式结果。
- 不能只有 `<f>公式</f>` 和空的 `<v/>`；有效数值缓存的简化示意为 `<f>公式</f><v>0</v>`。
- 计算并保存后，以最终文件重新读取验证；避免后续保存再次清空或覆盖缓存。
- 有依赖关系的公式结果应一起更新，不仅检查 D44/D45，也检查相关的 N6 和数据校验结果。

## 6. 上传前校验与打包顺序

### 6.1 业务与文件校验

校验最终保存到磁盘的 Excel，不能只检查内存里的计算变量：

1. 工作簿可正常打开，存在唯一的「核对汇总」页，表头符合原模板。
2. 店铺和月份正确；metadata 的 `shop_id` 继续使用平台店铺 ID，不改为财务店铺编码。
3. 千川获取状态明确；有数据或正常空数据时，均存在唯一、可被原公式匹配的“总计”行，C/D/I 是有效数字。
4. 对核对汇总的每条费用行检查：B 列资金账户和 C 列费用名称都存在时，D 列必须有有效数字；账户/费用名称只填一项也应报错。包括当前 D44、D45，不以两格通过替代全费用区块校验。
5. 数值结果不能是空、文本、布尔值、NaN、Infinity 或 Excel 错误。公式金额应是数值缓存，不是字符串公式结果。
6. 逐项核对 D44 等于源非赠款消耗的负数，D45 等于源总存入减赠款消耗，N6 与千川全部费用发生额一致；按原业务精度比较，不重复舍入。
7. H2/H3/H4 等数据校验结果也应有有效数值缓存。余额区块单独记录问题，不因费用为零就给未知余额造零，也不要把余额异常误报成费用失败。

若只剩独立余额异常，可沿用现有异常账单归档流程，明确保留余额待处理状态；不能标记为全部核对通过，也不因余额页尚未完成而无限重传已归档的正常费用。

### 6.2 最终产物与上传身份

严格按以下顺序执行：

```text
判定源数据状态
→ 生成源总计与费用结果
→ 保存公式和计算缓存
→ 重新打开最终 Excel 并校验
→ 计算最终 Excel 的字节数与 SHA256
→ gzip 打包
→ 计算实际 gzip 的字节数与 SHA256
→ 保存 metadata 与上传任务快照
→ 上传
```

- 修复后重新生成的文件属于新的计算运行，使用新的 `local_run_id`；不要拿已使用的运行 ID 配上变更后的内容，否则会触发 `409 RUN_CONTENT_CONFLICT`。
- 同一次上传的网络重试，继续复用原运行 ID、最终文件和业务快照；不要通过换 ID 规避冲突。
- `report` 对应最终原 Excel，`upload` 对应实际发送的 gzip；两个大小和哈希分别计算，不能沿用修改前的值。
- `upload.filename = report.filename + ".gz"`，multipart 附件文件名与其一致。
- `reconciliation_month` 继续使用 `YYYY-MM`；推荐文件名沿用 `YYYYMM【抖音】Y-店铺名称.xlsx`。不改变核对日期口径。
- 新运行上传后，云端按同平台、店铺 ID、月份更新原记录和企微原行；旧版本进入历史，不新增重复店铺行。

完整请求字段、身份头、回执和重试规则见[Mac 上传接口说明](mac-douyin-recon-upload.md)。本次不新增上传 API 字段。

## 7. 验收用例与完成标准

| 用例                           | 预期                                              |
| ---------------------------- | ----------------------------------------------- |
| 有数据，源总计 C=120.34、D=10、I=1000 | D44=-120.34；D45=990；最终缓存与公式一致                   |
| 成功获取且确认当月无发生                 | 生成零发生额总计；D44、D45 为数值 0；所有千川发生额均为零时 N6=0；费用区块可解析 |
| 有完整明细但无源总计                   | 按原字段口径生成唯一总计，不重复累加；无法确认明细完整时转为待处理               |
| 下载失败、无权限、超时，或空数据原因不明         | 明确报错并可重试；不走正常空数据分支，不自动补零后标记成功                   |
| 缺总计、重复总计、表头错位或源金额为空          | 生成阶段发现并提示具体原因；不能产出“费用校验通过”                      |
| D44 有值，但 D45 返回空字符串          | 上传前费用校验失败，指出 D45，不把文件标记为已就绪                     |
| 公式存在但缓存为空，或公式缓存为字符串 `"0"`    | 上传前校验失败；重算/正确写入缓存后才通过                           |
| 费用确认为零，但期初余额非零或余额截图缺失        | 正确保留真实余额/未知状态；不把账户余额批量置零；费用与余额状态分开              |
| 修复这 8 家后使用新运行上传              | 当前文件更新；费用汇总读取新版 D44/D45；数据校验不受余额问题影响；同店同月沿用企微原行 |
| 同一上传任务因网络失败重试                | 复用运行身份及产物，命中幂等记录，不新增历史版本或重复企微行                  |

交付时提供：正常有数据、确认无数据、获取失败三类本地用例结果，以及修复后这 8 家的最终 Excel 校验结果。费用验收以“最终文件金额正确且云端对应费用 Sheet 包含最新报告”为准。

上传接口的 `stored=true` 只表示归档成功。需要核验企微时，使用回执的 `report_id` 查询 `GET /api/douyin-recon/v1/reports/{report_id}`，检查 `data.sync.is_current` 及 `data.sync.sheets` 中「费用汇总」「数据校验」各自为 `synced`。余额仍缺数据时，整体 `sync.state` 可能为 `blocked`，不能据此把已经成功的费用页判为失败；也不能仅凭归档 HTTP 200/201 就宣称企微费用页已更新。
