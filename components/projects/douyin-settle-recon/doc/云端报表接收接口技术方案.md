# 抖音核对报表数据同步接口

版本：v1.3；日期：2026-10-19；状态：接口设计，待云端实现。

本机通过一个接口，将核对日期、核对月份、店铺信息和 `.xlsx.gz` 附件同步到云端。云端校验并解压，持久保存 Excel 和业务记录后返回成功。

配套：[OpenAPI 定义](云端报表接收接口.openapi.json)、[请求元数据示例](云端报表上传元数据.example.json)。

## 1 请求

```http
POST /api/douyin-recon/v1/reports
X-Invoice-Account-Id: <管理员注册的账号 ID>
X-Invoice-Worker-Token: <当前有效的 Mac Agent Token>
Content-Type: multipart/form-data; boundary=<客户端库自动生成>
```

鉴权沿用[发票管理 V2 技术方案第 7.4.1 节](<../../invoice-mac-agent/doc/2026-10-16_发票管理 V2 技术改造方案.md>)的 Mac Worker 独立凭据。两个请求头必须同时提供；云端校验账号已注册、Token 当前有效且属于该账号。不使用浏览器 Cookie 或 Authorization Bearer。

本次同步记录归首次创建它的账号所有，账号归属由校验通过的请求头确定，不从 metadata 接收或覆盖。重复同步时先检查运行的账号归属，其他账号不能上传或重复提交该运行；跨账号访问返回 404，不返回原记录及回执。Token 更新后，只要仍属于同一账号且有效，就可以继续重试原运行。

整个请求包含两个部分：

| 部分         | 类型                 | 必填 | 内容                                |
| ---------- | ------------------ | -- | --------------------------------- |
| `metadata` | `application/json` | 是  | 下述 JSON 元数据，可作为 JSON 文件部分上传       |
| `file`     | `application/gzip` | 是  | 一个 `.xlsx.gz` 附件，解压后只得到一个完整 Excel |

**只上传 gzip 附件，不上传原始 `.xlsx` 文件。** 不设置整个请求的 `Content-Encoding: gzip`，云端接收原始附件字节后自行解压。客户端库自动生成 multipart boundary。

## 2 元数据字段

| 字段                      | 类型     | 必填 | 说明                                                            |
| ----------------------- | ------ | -- | ------------------------------------------------------------- |
| `shop_id`               | string | 是  | 云端提供的店铺 ID，用于确定数据归属                                           |
| `shop_name`             | string | 否  | 店铺名称快照，只作展示                                                   |
| `local_run_id`          | string | 是  | 本次产出的运行 ID，使用 `manifest.run_id`；同时作为重复同步的识别依据                 |
| `reconciliation_date`   | string | 是  | 核对日期，`YYYY-MM-DD`，按北京时间记录                                     |
| `reconciliation_month`  | string | 是  | 核对的账单月份，严格为 `YYYY-MM`                                         |
| `reconciliation_status` | string | 否  | `matched` 完全一致、`different` 存在差异、`pending` 待确认；未提供时保存为 pending |
| `report`                | object | 是  | 解压后原 Excel 的元数据，不携带原 Excel 文件内容                               |
| `upload`                | object | 是  | 实际 gzip 附件的元数据                                                |

核对日期与账单月份分别保存。例如 `2026-10-18` 核对 `2026-08` 账单是合法组合。补传时沿用原核对日期，不改成上传日期。当前产物没有单独的核对日期字段，上传时需明确提供，不能把 `context.created_at` 的运行开始时间当成完成时间。

`report` 和 `upload` 字段：

| 对象字段                 | 类型      | 说明                                       |
| -------------------- | ------- | ---------------------------------------- |
| `report.filename`    | string  | 原 Excel 名称，`YYYYMM【抖音】Y-店铺名.xlsx`          |
| `report.size_bytes`  | integer | 原 Excel 字节数，大于 0                         |
| `report.sha256`      | string  | 原 Excel 的 SHA-256，64 位小写十六进制             |
| `upload.filename`    | string  | gzip 附件名称，必须等于 `report.filename + ".gz"` |
| `upload.compression` | string  | 固定 `gzip`                                |
| `upload.size_bytes`  | integer | gzip 附件实际字节数，大于 0                        |
| `upload.sha256`      | string  | gzip 附件的 SHA-256，64 位小写十六进制              |

文件名开头的 `YYYYMM`（兼容 `YYYY-MM`）必须与 `reconciliation_month` 一致。日期需通过实际日历校验；月份需满足 `^\d{4}-(0[1-9]|1[0-2])$`。云端根据鉴权后的账号校验店铺权限，不根据文件名猜测店铺归属。

元数据示例使用历史产物的大小和哈希。联调时替换真实 shop_id、运行 ID、日期、文件信息和哈希。

```json
{
  "shop_id": "REPLACE_WITH_CLOUD_SHOP_ID",
  "shop_name": "Y-兹伊翰官方旗舰店",
  "local_run_id": "20261018T152406Z-0f2ebd52",
  "reconciliation_date": "2026-10-18",
  "reconciliation_month": "2026-08",
  "reconciliation_status": "pending",
  "report": {
    "filename": "202608【抖音】Y-兹伊翰官方旗舰店.xlsx",
    "size_bytes": 31824648,
    "sha256": "f44636e49818ddab7ce6781bc0f8b1b9608eefe87645dd86a7dcb6488e1f8930"
  },
  "upload": {
    "filename": "202608【抖音】Y-兹伊翰官方旗舰店.xlsx.gz",
    "compression": "gzip",
    "size_bytes": 28243412,
    "sha256": "cfb6eef6e41252a9d57debb909f25173ce6175da205aa5ae9c52c54652deaa9f"
  }
}
```

## 3 调用示例

将元数据保存为 `upload-metadata.json`。`RECON_API_BASE` 为云端域名，`RECON_RUN_DIR` 为本次完整产物目录，`RECON_UPLOAD_FILENAME` 与 `upload.filename` 一致。`INVOICE_ACCOUNT_ID` 和 `INVOICE_WORKER_TOKEN` 沿用现有 Mac Worker 的账号 ID 和当前有效 Token。

```sh
curl --fail-with-body \
  --connect-timeout 10 --max-time 300 \
  -X POST "${RECON_API_BASE}/api/douyin-recon/v1/reports" \
  -H "X-Invoice-Account-Id: ${INVOICE_ACCOUNT_ID}" \
  -H "X-Invoice-Worker-Token: ${INVOICE_WORKER_TOKEN}" \
  -F 'metadata=@upload-metadata.json;type=application/json' \
  -F "file=@${RECON_RUN_DIR}/${RECON_UPLOAD_FILENAME};type=application/gzip"
```

本机从 `manifest.report_gzip` 选取附件，从 `manifest.report` 获取原 Excel 元数据；上传前重新校验两个文件的大小和哈希。不要从 doc 目录选取预期结果表。

## 4 云端接收处理

1. 校验两个请求头中的账号与 Token 绑定关系、Token 有效性；已有 local_run_id 必须归当前账号所有，归属不符返回 404。再校验该账号对 shop_id 的权限，以及必填字段、日期月份和附件名称。
2. 流式接收 gzip 到临时区，计算实际大小和 SHA-256，与 upload 字段校验。
3. 由业务代码完整解压 gzip，校验解压后的 Excel 大小、SHA-256 和基本工作簿结构，与 report 字段核对。不重新计算财务结果。
4. 将解压后的 Excel 持久保存，写入其关联的创建账号、店铺、运行 ID、核对日期、月份和可选核对状态。创建账号取自已验证的 X-Invoice-Account-Id，保存后不得通过其他账号的请求改写。文件保存与数据库提交均成功后，才能返回成功。
5. 成功后清理临时 gzip；清理失败可后台重试，不撤销已成功的同步。云端长期保存 Excel 和上传元数据。

gzip 接收大小和解压后大小均设置上限，流式处理过程中检查。文件损坏、哈希不符或存储失败时不能返回成功。若文件已保存但数据库失败，应按失败处理并清理未被记录引用的残留文件。

## 5 响应

首次同步成功返回 HTTP 201；同一内容重复同步返回 HTTP 200，`duplicate=true`，复用原 report_id。

```json
{
  "code": "OK",
  "message": "同步成功",
  "data": {
    "report_id": "rpt_01",
    "local_run_id": "20261018T152406Z-0f2ebd52",
    "stored": true,
    "duplicate": false,
    "excel_sha256": "f44636e49818ddab7ce6781bc0f8b1b9608eefe87645dd86a7dcb6488e1f8930"
  }
}
```

| 字段                  | 说明                                          |
| ------------------- | ------------------------------------------- |
| `code`              | 成功固定为 OK                                    |
| `data.report_id`    | 云端保存的记录 ID                                  |
| `data.local_run_id` | 本次同步的本机运行 ID                                |
| `data.stored`       | 仅在 Excel 持久保存并完成记录入库后为 true                 |
| `data.duplicate`    | 是否命中已有相同记录                                  |
| `data.excel_sha256` | 云端已保存 Excel 的 SHA-256，需与本地 report.sha256 一致 |

本机确认 HTTP 成功、code=OK、stored=true、运行 ID 和 Excel 哈希一致后，才将该次同步标记为完成并保存回执。同步成功只表示文件与业务记录已保存；pending 或 different 报表可以同步，原核对结论保持不变。

## 6 重复同步与重试

云端以 local_run_id 识别该业务域内唯一的一次同步，记录首次创建账号，并建立运行唯一约束。重复请求先检查当前账号是否为创建账号，再执行下面的内容比较；不能仅按“账号＋运行 ID”另建记录绕过已有运行的归属检查。无需另设幂等请求头。

- 同一运行、相同业务字段和相同原 Excel 名称、大小、哈希，返回已有记录。
- 已有运行属于其他账号时返回 404，不能覆盖，也不能返回该账号的已有回执。并发创建时也必须在唯一约束冲突后重新核验创建账号。
- 同一运行的 shop_id、核对日期、月份、名称快照、核对状态或原 Excel 发生变化，返回 HTTP 409，不能覆盖旧记录。
- shop_name 未传按 null 保存，reconciliation_status 未传按 pending 保存，再比较是否一致。
- 同一 Excel 重新 gzip 压缩可能产生不同压缩字节；仍须校验本次 gzip 和解压内容，原 Excel 和业务字段相同则视为重复同步，保留首次成功的传输元数据。
- 新的计算运行使用新 local_run_id，另存一条记录。并发重传通过数据库唯一约束保证不重复保存。

网络超时、断线、429 或临时 5xx 错误时，保留原元数据和文件，使用同一账号及其当前有效 Token，沿用原 local_run_id 重传这个接口。即使上一次请求已保存但回执丢失，也会返回该账号的原成功记录。400、401、403、404、409、413、415、422 应修正请求或配置后再处理，不盲目重试。

## 7 错误响应

| HTTP      | code                             | 含义                              |
| --------- | -------------------------------- | ------------------------------- |
| 400       | `INVALID_REQUEST`                | 缺 multipart 部分、JSON 无法解析或必要字段缺失 |
| 401       | `UNAUTHORIZED`                   | 任一鉴权头缺失、账号未注册、Token 无效或与账号不匹配   |
| 403       | `SHOP_FORBIDDEN`                 | 无该店铺的同步权限                       |
| 404       | `RUN_NOT_FOUND`                  | 运行不存在或不可访问；已有运行不属于当前账号时返回       |
| 409       | `RUN_CONTENT_CONFLICT`           | 同一运行对应不同业务数据或 Excel             |
| 413       | `FILE_TOO_LARGE`                 | gzip 或解压后文件超过配置上限               |
| 415       | `UNSUPPORTED_FILE_TYPE`          | 直接上传 xlsx 或其他不支持的附件             |
| 422       | `INVALID_METADATA`               | 日期、月份、压缩类型或文件名关系不合法             |
| 422       | `FILE_HASH_MISMATCH`             | 大小或哈希不匹配                        |
| 422       | `INVALID_GZIP` / `INVALID_EXCEL` | 压缩文件损坏或解压后不是有效工作簿               |
| 429       | `RATE_LIMITED`                   | 请求限流，按 Retry-After 重试           |
| 500 / 503 | `STORAGE_UNAVAILABLE`            | 未确认持久保存成功，可沿用原运行重试              |

```json
{
  "code": "FILE_HASH_MISMATCH",
  "message": "gzip 附件 SHA-256 与 upload.sha256 不一致",
  "details": { "field": "upload.sha256" }
}
```

失败时使用对应 HTTP 状态码，不以 HTTP 200 包装失败。
