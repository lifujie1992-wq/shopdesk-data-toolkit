# 抖音月度财务账单自动核对实现方案

版本：v3 店铺归属与云端全量交付版。更新日期：2026年10月18日。

**确定职责：本机只执行shopdesk抓取、数据加工、Excel汇总核对及上传；所有业务数据携带店铺归属推送云端，长期存储、查询下载、企微路由与消息推送全部由云端执行。**

采用“shopdesk 负责登录与采集，本项目负责账单处理、计算和报表”的结构。以现有 Excel 模板作为计算依据，每月处理上一个自然月，输出单店完整核对工作簿、差异明细和执行清单，将原始账单、截图、结构化明细、计算结果和最终Excel按店铺归属上传原云服务器；最终Excel压缩为gzip。云端接管归档、查询、下载、企微发送和后续重试。先用现有 2026 年 8 月样例验证计算，再接入自动下载，最后启用多店月度任务。

## 需求范围

需求依据为本目录下的 [PRD](抖音电商月度财务账单自动核对_PRD.docx)、[下载路径说明](【抖音】店铺月账单下载路径.docx)、[处理模板](【抖音】月度账单处理模版.xlsx) 和 [2026年8月样例](202608【抖音】Y-兹伊翰官方旗舰店.xlsx)。PRD 定义计算口径，下载说明补充采集范围，样例用于验证实际处理方式和发现输入差异。

| 处理对象  | 采集内容             | 处理与输出                        |
| ----- | ---------------- | ---------------------------- |
| 资金账单  | 目标月明细、月汇总、余额页面截图 | 原始表、加工明细、货款账户发生额及余额核对        |
| 结算账单  | 目标月结算明细          | 原始表、结算金额校验                   |
| 管家账户  | 各主体流水、各主体余额及截图   | 分主体保留明细，按模板归类，输出账户核对         |
| 基础保证金 | 目标月流水、余额截图       | 原始流水、加工明细、账户核对               |
| 体验保证金 | 目标月流水、余额截图       | 原始流水、加工明细、账户核对               |
| 涉税账单  | 各主体目标月明细         | 下载、按主体归档和附表输出；现有模板没有对应税务核算公式 |

资金账单的日期依据为动账时间，结算账单依据为结算时间，其他流水依据各自账务时间。统一使用北京时间，内部区间为“本月1日00:00:00 ≤ 时间 < 下月1日00:00:00”，不能按订单下单时间过滤。

单店输出命名为 `YYYYMM【抖音】店铺名.xlsx`。主体明细和截图保留主体标识；店铺名称改变不影响内部店铺标识和历史归档。

最终交付包括云端按店铺保存的全部原始数据与计算产物、完整 `.xlsx.gz`、稳定下载入口和云端发到指定企微群的核对摘要。gzip符合企微文件限制时同时发送gzip附件；超限时以长期下载链接交付完整文件，不拆分或截断工作簿。分别记录生成、压缩、云端保存和消息发送状态，云端持久保存及所需企微消息发送均成功后才算完成交付。

## 模板和样例中的关键事实

| 位置       | 核实结果                                     | 实现要求                        |
| -------- | ---------------------------------------- | --------------------------- |
| 模板工作表    | 共8张，包含原始账单、余额截图、资金账单加工、核对汇总和映射表          | 保留现有核心工作表，新增附表承载来源和差异       |
| 资金加工表    | A～AM为39个输入字段，AN～AQ为4个加工字段                | 按字段名写入；AQ由来源账户决定            |
| AN2、AP2  | 使用 `_xlfn.IFS`，保存为数组公式                   | 提取真实公式文本，不能仅处理普通公式字符串       |
| 映射表      | 32条有效映射，工作表尺寸却到13325行                    | 按有效数据识别记录数，忽略仅有格式的空行        |
| 核对汇总     | D2～D43共42个账户费用项目；H2～H4做结算核对；L2～P5做账户余额核对 | 逐项实现原公式，不能用统一透视表替代全部计算      |
| 汇总M列、P列  | 模板期初余额和余额校验没有完整输入或公式                     | 补充有来源的余额输入与差异输出，不把空值当0      |
| 样例资金账单   | 29896条原始流水                               | 可与月汇总截图的29896笔交叉校验          |
| 样例加工表    | 29900条，其中4条为追加的体验保证金流水                   | 加工表包含多个账户来源，不能只处理资金账单       |
| 样例保证金追加行 | 金额有正负，动账方向为空，日期和流水号未带入加工表                | 保留模板计算语义，同时在来源附表补齐可追溯关系     |
| 结算账单字段   | 模板45列，样例46列；样例增加APP渠道，且“店铺劵”与“店铺券”写法不同   | 建立显式字段别名；新增列保留原值，禁止按列序号直接拷贝 |
| 样例映射引用   | AP公式指向外部工作簿，本文件没有映射工作表                   | 正式输出将已确定的映射表内置，消除外部工作簿依赖    |
| 样例余额依据   | 货款截图为目标月月汇总；保证金和管家截图显示当前余额               | 区分目标月期末与采集时点余额              |

样例结算账单的24201条明细，以十进制求和为 **1467515.09元**。样例资金月汇总截图显示：期初 **36139.32元**、本期变化 **-7739.19元**、期末 **28400.13元**。这些可作为回归核对点，但样例缓存值不能代替重新计算。

按模板当前32条映射和AP特殊规则回放，样例有48条不能得到原样例的分类：`评价有礼`23条、`以旧换新`21条、`快递拦截费`4条。其原样例缓存分类依次为“评价有礼”“货款收入-平台补贴”“拦截费”。应将这3条列为候选补充映射，完成业务口径核实后纳入带版本的规则集，不能默默归到“其他”。

## 总体结构

```text
月度调度或手工指定月份
        ↓
本项目任务编排与采集清单
        ↓ 本机鉴权接口
shopdesk 店铺列表和独立登录会话
        ↓
财务页面内请求 → 生成报表 → 历史报表轮询 → 下载与截图
        ↓
原始文件和采集元数据归档
        ↓
解析与完整性检查 → 模板规则计算 → 账户和结算核对
        ↓
Excel 报表、差异明细、机器可读结果
        ↓
本机生成按店铺归属的manifest → 上传原始数据、截图、结果及 .xlsx.gz
        ↓
云端按店铺验证全量产物 → 完整批次提交 → 持久归档
        ↓
云端通知队列 → 企微核对摘要、长期下载链接和可发送的gzip附件
```

本项目建议使用 Python、openpyxl、Decimal 和 SQLite。Python负责文件处理和编排，openpyxl负责工作簿读写，Decimal负责十进制计算，SQLite保存采集状态与核对结果。shopdesk侧增加小范围的 Electron 财务采集模块，复用现有会话和本机接口。本机负责采集、计算、报表、gzip及上传；SQLite只保存本机执行检查点和待上传缓存。原云服务器是业务数据的长期事实来源，负责完整接收、存储、查询、下载、企微路由、发送及通知重试。

### 本机与云端职责

| 本机Mac | 原云服务器 |
| --- | --- |
| 使用shopdesk店铺会话采集账单和截图 | 管理统一店铺档案、接收机器及店铺映射 |
| 解析数据、执行模板规则、汇总核对并生成Excel | 接收并校验按店铺归属的全部数据与文件 |
| 生成结构化明细、结果、manifest及Excel的gzip文件 | 长期归档原始账单、截图、明细、计算结果及报表版本 |
| 上传所有产物，失败时恢复未完成上传 | 提供店铺、月份、批次查询及长期下载 |
| 收到完整批次保存ACK后结束本机任务 | 依据云端群配置发送企微消息、补发并记录交付结果 |

本机不承担长期下载服务、企微群路由、Webhook管理或云端通知补发。云端不重复实现Excel财务计算；需要重算时由本机用固定输入与规则版本生成新的批次并重新交付。此处“全部数据”指本业务的账单及计算产物，登录Cookie、shopdesk令牌、上传API密钥等不作为业务数据上传。

## shopdesk 采集复用方案

### 可以直接复用的能力

已核实的本机实现位于 [agent-api.js](/Users/zhaoxiaozhong/shopdesk-workbench-src/src/agent-api.js)、[exploration.js](/Users/zhaoxiaozhong/shopdesk-workbench-src/src/exploration.js) 和 [main.js](/Users/zhaoxiaozhong/shopdesk-workbench-src/src/main.js)。现有售后采集的调用方式可参考 [scrape\_counts.py](/Users/zhaoxiaozhong/projects/shopdesk-aftersale/bin/scrape_counts.py)。

- 从 `~/Library/Application Support/shopdesk/agent-bridge.json` 读取动态端口和令牌，通过 `POST http://127.0.0.1:{port}/call` 调用；配置和令牌只在本机读取，不写入报表或日志。
- `list_shops` 获取店铺UUID、名称和平台，限定采集抖店。
- 使用 `persist:shop-<shop_id>` 的独立 Electron session，复用用户在shopdesk中的登录状态。
- `start_exploration`、`exploration_command`、`close_exploration` 支持官方页面导航、页面内执行请求、查看网络事件和响应。
- 工作台已有 `capturePage()` 截图实现，可以复用实现方式。

现有探索接口适合开发时确认财务页面和请求，但不是完整的财务采集器：未暴露下载管理及截图命令；单次脚本执行限时10秒，命令外层限时15秒，返回内容限制约2MB；探索页面全局只有一个，空闲5分钟关闭。本机接口按调用串行，但多次调用组成的整段探索流程没有跨客户端独占保护。

因此，账单大文件不通过 `Runtime.evaluate` 返回Base64，不在一次脚本里等待长时间生成报表，也不通过复制Cookie建立另一套登录系统。

### 建议新增的财务采集能力

在shopdesk新增 `src/finance.js`，由 `main.js` 初始化，并在 `agent-api.js` 挂载以下接口。以下名称均为拟新增接口。

| 接口                     | 输入要点                 | 返回与作用                   |
| ---------------------- | -------------------- | ----------------------- |
| `finance_capabilities` | 无                    | 协议版本、可采账单、下载与截图支持情况     |
| `finance_start`        | 店铺UUID、月份、账单类型列表、幂等键 | 立即返回job_id，后台执行采集       |
| `finance_status`       | job_id               | 分阶段进度、主体清单、报表任务ID、文件及错误 |
| `finance_cancel`       | job_id               | 取消本任务，释放属于本任务的资源        |
| `finance_artifacts`    | job_id               | 本地文件路径、大小、SHA-256、来源和账期 |

`finance_start`内部逐店、逐主体执行，在对应店铺会话里打开官方页面，读取实际店铺和主体身份，再发起页面内请求。财务请求路径、参数、金额单位和时间字段需在开发阶段通过真实页面确认；下载说明只定义页面路径，不能据此编造后台API。

任务元数据保存在shopdesk的 `business-data/finance/` 下，文件也先下载到此受控目录。本项目通过产物清单校验后复制到本机工作缓存，用于计算和完整上传；长期归档由云端负责。接口返回路径和元数据，避免大文件穿过本机JSON响应。

### 单份账单的执行流程

1. 确认登录、财务权限、店铺身份和主体身份；需要扫码或额外验证时返回明确状态。
2. 选择账单类型、目标月份及账户。月份和主体必须同时在页面状态或响应中核实。
3. 先查找本任务已有的报表ID；可复用时继续轮询，避免重试重复生成。
4. 需要生成时提交报表任务，持久化平台报表ID、参数、提交时间及账期。
5. 分次查询历史报表，按报表ID、店铺、主体、账单类型和账期匹配，不能下载“最新一条”代替精确匹配。
6. 通过该session处理下载，关联发起页面与任务，下载到临时文件，完成后校验文件格式、可解析性、大小和哈希，再原子重命名。
7. 文件含分片或压缩包时全部下载；解包后生成逐文件清单，核对明细总数及金额。
8. 对余额页面读取结构化数据并截图，记录截图时间、页面日期、主体及余额口径。

过期下载链接重新获取，报表生成未完成则保存状态稍后重试。只有平台明确返回目标账期无流水，才记为 `no_activity`；下载失败和空文件不能当作0条流水。

### 多主体和任务并发

管家账户、涉税账单需枚举全部可见主体并逐个处理，切换后检查实际主体ID，不能仅依赖下拉框文字。基础保证金、体验保证金分别作为独立账户类型采集。

内部保留 `shop_uuid`、平台店铺ID、主体ID和平台账户ID。样例中的店铺编码 `14132514` 不能当作shopdesk UUID。历史主体也需要保留，不能只按当前营业主体过滤历史流水。

同一主体钱包如被多个店铺入口展示，先确认是否为同一个平台账户；同一账户同一账期的余额不能在多店总览中重复累加。

首版对财务采集串行执行。后台任务需要共享的资源锁：涉及同一店铺会话和主体切换的其他采集任务也必须遵守，避免互相改变上下文。探索接口被其他任务占用时排队或返回 `busy`，不强行关闭别人的探索页。取消及清理操作校验job所有权；长任务释放本机调用队列，状态查询保持可响应。

## 数据处理和计算口径

### 原始数据与字段匹配

原始下载文件以不可变产物上传云端保存，本机保留计算与上传所需的工作缓存。原始工作表保留平台列名、顺序和原值，加工表A～AM按模板字段名投影；模板未覆盖的新列保留在原始表和字段检查清单中。每行保存来源文件、工作表、原始行号、主体和账户。

字段匹配先精确匹配，再使用显式别名表，例如已经发现的“店铺劵／店铺券”。缺失必需列、重名列、无法识别的金额或日期会阻止最终核对；可选列需有明确的空值处理规则。原始的空白、数字0和字符串保持可区分。

流水号、订单号、商品ID等按文本处理。原始值中的前导单引号、制表符保留在原始层；另生成用于关联的规范值，不能将长编号转成浮点数。

重复下载通过文件哈希与采集清单避免重复入账。同一文件中的合法重复行不按“整行相同”直接删除；只有平台稳定的流水标识或已确认的复合键才能用于业务去重。

### 统一加工明细

货款流水按原始39列进入加工表。管家及保证金流水通过各自适配器进入同一加工明细：金额映射到D、场景映射到F、备注映射到AM，AQ填写对应账户；时间、操作单号等来源字段在有明确对应关系时映射，完整来源始终保留在附表。

保证金金额本身可能已经带正负，动账方向为空时按AN默认分支使用原金额，不能再对负数重复取反。账户类型必须来自采集上下文，不能因为原始E列写“聚合账户”而把所有来源认定为同一资金账户。

### AN到AQ的规则

| 列      | 规则                          |
| ------ | --------------------------- |
| AN结算金额 | C为“入账”时取D；C为“出账”时取-D；其他情况取D |
| AO订单收入 | `SUM(Q:AB)-R`，逐行执行          |
| AP费用类型 | 按下表的模板优先级执行，命中即停止           |
| AQ资金账户 | 按真实来源填写货款、管家、基础保证金或体验保证金账户  |

AP的现有优先级如下，所有关键词均检查AM备注：

| 顺序 | 条件                | 费用类型                          |
| -- | ----------------- | ----------------------------- |
| 1  | 包含“运费”            | 运费赔付                          |
| 2  | 包含“管家账户充值”        | 管家账户充值                        |
| 3  | 包含“聚合账户充值至管家账户”   | 管家账户充值                        |
| 4  | 包含“充值保证金”         | 保证金充值                         |
| 5  | 包含“充值巨量千川”        | 巨量千川充值                        |
| 6  | 包含“超”             | 超时赔付                          |
| 7  | 包含“消费者”且不含“超”“运费” | 消费者赔付                         |
| 8  | F动账场景不为空          | 在账单字段对照表中精确查找，保持VLOOKUP首条匹配语义 |
| 9  | F为空               | 取AM备注前3个字符                    |

例如备注含“退换货运费险”时，先命中“运费”，按模板归为“运费赔付”。实现不得凭业务直觉改回运费险。原始备注也不能先清理、改写后再参与匹配。

没有映射、落入没有汇总项目的分类，或者同一场景配置了冲突映射时，保存原因和来源，列入待确认清单。保留“模板计算出的类别”和“数据检查状态”两套字段，不能用“未匹配”覆盖原公式结果后继续声称计算一致。

### 核对汇总

- D2使用AO，条件为账户和费用类型；D3、D4、D5、D6分别对加工表AC、AD、AG、AH整列求和。
- D7～D43按对应账户和费用类型汇总AN，完整保留模板42个项目。
- H2为 `SUM(D2:D9)+D31+D37`，H3为结算账单D列合计，H4为 `H2-H3`。
- N2～N5按模板账户条件汇总D列，O为M期初余额加N本期发生额。
- 为每个账户补充实际期末余额和来源，P列展示“计算期末余额－实际期末余额”。

模板的 `SUMIF(B:D,L2,D:D)` 使用多列条件区域，实现前需在Excel或WPS中以非零测试数据验证其实际求值范围，再冻结与模板等价的账户汇总规则，避免直接把异常写法解释成另一种口径。

服务商佣金、渠道分成、其他分成等字段存在于明细，但现有汇总没有全部逐列列出。保留原公式，并额外检查这些非零金额是否得到模板覆盖；发现未覆盖时列入核对问题，不擅自增加费用口径。不同校验之间的内部划转或同一流水组件不能重复计入。

### 公式与金额实现

系统从模板提取公式文本、数组公式、映射内容及汇总坐标，生成规则清单和版本哈希。计算引擎只实现清单内的公式语义；模板变更时做差异检查，未支持的公式不能悄悄跳过。

金额使用原始数值精度的Decimal；源文件以分提供金额时显式转换成元，不根据数字大小猜单位，不为凑平差额逐行取整。Excel空白、数字和文本的行为在规则层明确处理。

样例缓存H4约为 `4.43×10^-7` 元，P2约为 `-3.76×10^-6` 元，属于需要识别的旧浮点尾差。正式计算用源账单和有来源的余额进行十进制运算，差异必须严格为0；不设置“1分钱以内视为一致”的容差。旧缓存回归时同时保存原缓存值和按源金额精度展示的比较结果。

openpyxl不执行公式。首版由Python计算并用XlsxWriter等支持公式缓存值的写出库生成报表，关键公式同时写入公式和本次计算结果，截图重新嵌入；不能只写公式并等待用户打开Excel才得出结论。输出设置重新计算，并使用Excel或WPS对代表性报表重算交叉验证。若选择用openpyxl保留模板样式，则需额外实现和验证缓存值写入，不能把该步骤省略。

## 余额来源和最终结论

### 历史余额取值

货款账户优先使用目标月资金月汇总中的期初、期末和发生额，分别与明细计算交叉核对。首次运行不从0开始；没有月汇总的账户需要已确认的期初余额，或同一账户上月已核对的期末余额，保留来源与版本。

按下载说明，无需选择日期的管家、保证金截图是采集时点证据。样例管家截图页面日期已到9月11日，不能据此独立证明8月31日余额。余额记录必须分别保存 `captured_at`、`balance_as_of` 和余额口径，并区分总余额、可提现余额、冻结余额。

历史期末余额优先从官方历史账单或历史余额数据读取。如平台只提供当前余额，可在取得目标月末至截图时点的完整流水、验证时间边界和完整性后反推历史余额，并标注为“流水反推”。无法取得充分证据时保留截图，账户状态为待确认。截图OCR只辅助录入，不独立决定最终核对结论。

原样例管家余额为3个主体的 `4.02+0.96+14.50=19.48` 元。正式处理保留分主体取值及口径，只有相同余额时点和口径的数据才合并到模板的管家账户汇总。

### 结论判定

将执行状态与财务结论分开：执行状态包含等待报表、需要登录、采集失败、待确认和已完成；已完成且输入完整的核对才进入PRD规定的二元结论。

| 条件                               | 报表状态                         |
| -------------------------------- | ---------------------------- |
| 必需账单和账户齐全，规则确定，余额时点有效，所有规定差异严格为0 | 完全一致                         |
| 必需输入和规则完整，任一规定差异不为0              | 存在差异，并列出全部差异                 |
| 缺账单、无有效余额、映射未确定、文件或计算异常          | 待完成／待确认，保留已计算的差异，不发布最终“完全一致” |

涉税账单按下载说明纳入月度交付完整性检查；由于模板没有涉税核算规则，其下载完成不代表完成税务核对。

差异明细至少包含店铺、主体、账户、项目、预期值、实际值、差异、来源文件和行号、命中规则及问题类型。额外检查各来源账户的原始净发生额与模板账户发生额是否覆盖一致，用于发现已下载但未进入汇总的流水。


## 存储和交付

建议目录如下，本机目录用于执行和上传缓存，长期业务数据保存在云端：

```text
douyin-settle-recon/
  doc/                         需求、模板、样例和实现方案
  src/douyin_settle_recon/      编排、解析、规则、核对和输出
  config/                      店铺选择、字段别名和版本化配置
  tests/                       计算与采集契约测试
  deploy/                      macOS月度调度配置
  data/recon.sqlite            本机检查点、计算缓存及上传状态
  data/raw/YYYYMM/shop_uuid/    主体及账户原始文件和截图
  data/runs/run_id/             本次输入清单、规则版本及结果
  reports/YYYYMM/shop_uuid/     完整工作簿、gzip文件和结果
  data/outbox/                 本地待上传清单与重试状态
  server/                      云端接收、下载和企微通知模块
```

本机SQLite保存执行与计算缓存，如 `runs`、`collection_tasks`、`artifacts`、明细缓存、规则快照和 `upload_outbox`。这些业务记录均作为结构化数据随批次上传；本机不作为长期查询或交付记录的唯一来源。明细保留来源键和类型，金额以十进制文本或明确单位整数保存，不使用REAL做财务累计。云端保存完整run、店铺关联、全部产物、明细、校验结果、版本和通知记录。

每次运行固定输入文件清单、文件哈希、模板哈希、规则版本、余额来源版本和程序版本，随manifest和规则快照全部上传云端。同店同月重跑生成新运行记录，复用已验证下载；重算不要求再次访问平台。新运行失败不覆盖上一份成功报表，新结果完成后再原子更新最新索引。

工作簿保留8张模板核心表，补充“核对结论”“差异明细”“采集清单”“余额依据”“字段检查”“来源明细”，保证金截图单独放入“保证金截图”；管家账户流水与对应主体截图放在同一工作表的不同区域，需要分表时保留清晰索引。涉税账单按主体作为附表或独立文件归档。

大数据量按工作表容量分片，内部计算覆盖全部明细，不受Excel单表行数限制。机器可读结果包括财务结论、执行状态、输入完整性、各项校验和报表路径。

## 云端长期存储与企微推送

### 上传的店铺归属

每个业务批次只归属一个店铺和一个月份。以云端统一 `shop_id` 作为归属键，`platform=douyin` 与平台店铺ID用于核对身份；`shop_name`只作展示。shopdesk的本机店铺UUID作为来源标识保存，不能替代跨电脑的统一店铺ID。

本机先根据shopdesk店铺UUID及页面核实的平台店铺ID，匹配云端已有店铺档案；映射关系包含 `agent_id`、`shopdesk_shop_uuid`、`platform_shop_id` 和云端 `shop_id`。多台电脑采集同一平台店铺时应落到同一云端shop_id。未知、冲突或缺少真实店铺身份的任务待确认，不按店铺名称猜归属，不将本机UUID直接注册成另一家店。

上传API鉴权时校验本机身份和可上传店铺范围，metadata、manifest和每项产物的归属必须一致。主体ID和资金账户ID作为店铺下的业务维度保留；多主体钱包的共享关系由云端统一记录，跨店查询时避免重复汇总同一实际账户。

### 全量业务数据清单

每个批次上传manifest及下列业务产物，不能只上传最终Excel：

| 产物类型 | 云端接收内容 | 归属与完整性 |
| --- | --- | --- |
| 原始账单 | 资金、结算、管家、基础保证金、体验保证金、分主体涉税账单及全部分片 | 店铺、月份、主体、账户、平台报表ID、原文件哈希与行数 |
| 截图和余额证据 | 资金月汇总、保证金、各主体管家截图及结构化余额 | 页面账期、采集时间、余额时点、来源账户与主体 |
| 结构化明细 | 各来源规范化流水、加工字段AN～AQ、原始行与文件关联 | 使用JSONL等机器可读格式，可逐文件gzip压缩；金额为十进制文本 |
| 计算结果 | 分类汇总、账户余额核对、结算核对、差异、未匹配和字段检查 | 与最终Excel同一计算批次、规则版本和行数 |
| 最终报表 | 每店每月完整Excel的 `.xlsx.gz` | gzip及解压后Excel各自的字节数和SHA-256 |
| 运行依据 | 输入清单、模板或模板快照、映射及规则快照、程序版本、脱敏执行与错误记录 | 可重现本次输入及计算规则，不包含登录凭据 |

gzip只封装一个完整文件，不能把多个文件拼接后误称为 `.xlsx.gz`。原始账单及截图可按原格式上传，或单文件gzip传输并保存原文件名、大小及哈希。manifest逐项声明类型、逻辑路径、主体、账户、原始与传输哈希、大小、行数及来源。平台确认无流水时记录 `no_activity` 证据；失败或缺失项必须如实声明，不能伪装成空文件。

### 本机打包与完成边界

本机校验Excel可打开，流式生成 `.xlsx.gz`，保留原Excel和gzip哈希；使用固定gzip时间戳等确定性参数。JSONL等结构化结果与Excel来自同一次计算，不在上传阶段重算。所有产物写入按店铺和月份组织的manifest，逐文件上传，避免大文件通过JSON/Base64或一次巨大的multipart请求传输。

本机的必要缓存和上传队列在云端完整保存ACK前保留。只有manifest要求的全部产物已被云端校验并确认持久保存，才将本机批次记为 `uploaded_complete`。之后本机可按缓存策略清理已确认的工作文件；未收到完整ACK的产物不能清理。此处不实施实际删除，具体缓存期限在部署配置中确定。

本机任务不等待企微最终发送结果，也不实现企微重试。可查询展示云端交付状态，但无须持续在线。整体业务交付完成与本机任务完成分别记录：前者还要求云端发送成功，后者以完整数据交接成功为边界。

### 云端接收与查询接口

接口部署在原云服务器的独立业务模块或路由中。以下为拟新增契约，具体域名和部署目录实施时核实。

| 接口 | 用途 | 关键行为 |
| --- | --- | --- |
| `GET /api/douyin-recon/v1/shops/resolve` | 解析店铺归属 | 使用已鉴权agent及平台店铺ID匹配已有云端shop_id，不按名称猜测 |
| `POST /api/douyin-recon/v1/runs` | 创建单店单月批次 | 接收归属信息与manifest，返回run_id、已接收及待上传产物 |
| `PUT /api/douyin-recon/v1/runs/{run_id}/artifacts/{artifact_id}` | 幂等上传单项产物 | 流式接收二进制，校验归属、类型、大小和哈希，返回产物保存状态 |
| `POST /api/douyin-recon/v1/runs/{run_id}/complete` | 提交完整批次 | 核对manifest全量文件、结构化数据及必需项；完整保存后返回ACK并创建云端后续任务 |
| `GET /api/douyin-recon/v1/runs/{run_id}` | 查询批次 | 返回店铺归属、缺失项、保存与入库状态、下载入口及企微发送状态 |
| `GET /api/douyin-recon/v1/shops/{shop_id}/runs` | 云端历史查询 | 按店铺、月份、版本和状态查询批次 |
| `GET /runs/{run_id}/artifacts/{artifact_id}/download` | 长期下载 | 受控下载完整报表或其他归档产物 |
| `POST /api/douyin-recon/v1/runs/{run_id}/retry-notification` | 云端通知补发 | 鉴权；已成功项不重发，结果不确定项先核实 |

创建批次的metadata至少包含 `schema_version`、`agent_id`、本机run_id、云端 `shop_id`、`platform`、`platform_shop_id`、`shopdesk_shop_uuid`、店铺名称快照、月份、报表版本、模板及规则版本、生成时间、核对状态及差异项目数。若结论尚未确定，必须如实标记。云端不信任客户端提供的名称来决定归属，校验API身份和统一店铺映射。

幂等键绑定云端shop_id、月份、报表版本及manifest哈希，云端核验清单与文件；相同键相同内容返回已有批次，相同键不同内容返回冲突。单文件按artifact_id和哈希幂等上传。请求超时后查询缺失产物并续传，不重复计算、归档或通知。

云端先暂存并校验原始/传输文件哈希，gzip在受限资源内验证解压完整性，结构化明细按明确schema入库，不重新计算财务结果。`complete`核对所有必需产物、合法无流水标识、行数及归属。产物缺失、归属冲突或损坏时返回具体缺口，不返回完整ACK、不发送正式报表。异常批次允许保存已有数据用于排查，但必须标记为未完成。

全部产物完整保存后，在数据库事务中标记 `stored_complete` 并登记云端后续任务，返回 `data_received_complete=true` 与 `processing_status=queued`。这是本机可结束的交接凭据，不等于企微已发送。文件落盘、结构化入库和任务登记异常中断需能在云端核对恢复。

云端后续任务统一执行归档索引、访问入口生成、店铺到企微群路由、文件上传、消息发送和失败重试。原先仅接收单个报表文件的接口不再作为完整交接契约；最终Excel只是该批次中的一种产物。

### 长期保存和下载

云端按统一shop_id、月份、run_id及报表版本保存全部原始账单、截图、结构化明细、核对结果、规则快照和完整报表gzip，产物元数据按artifact_id关联；历史版本不覆盖、不自动过期删除。部署时配置持久数据目录、备份和容量监控；以后需要保留期限时再明确清理规则。

下载使用稳定run_id、artifact_id和受控访问凭证，长期有效；不能把企微media_id或短期签名地址当作唯一入口。归档文件位于受控存储目录，通过下载接口读取。凭证必要时可撤销或轮换，但不删除归档文件。

下载响应使用附件方式，文件名以 `.xlsx.gz` 结尾，不设置会让浏览器透明解压的 `Content-Encoding: gzip`，保证下载字节与归档哈希一致。企微摘要说明“解压后获得Excel工作簿”。

### 云端发送企微消息

企微机器人Webhook、店铺到群的映射、限速与重试队列都运行在原云服务器。本地无需保存企微密钥，也不需要在线等待云端补发。

完整批次交接成功后，云端根据统一shop_id选择对应企微群，发送月份、店铺、结论、差异项目数、报表版本和长期下载入口。正式通知不得在仅收到Excel或部分原始数据时提前触发。依照[企业微信官方说明](https://developer.work.weixin.qq.com/document/path/91770)，普通文件当前上限20M：gzip符合限制时先上传机器人文件素材并发送gzip附件，再发送含长期链接的摘要；超限时发送摘要和完整gzip的长期下载链接，文件状态标记 `link_only`，不拆分数据、不误报附件成功。

“完全一致”和“存在差异”的正式报表均推送。未完成或待确认任务可发送明确标注状态的异常摘要，不能冒充正式核对结论。素材media_id只供上传它的机器人使用，3天有效期用于消息发送，过期重试重新上传素材，云端归档与长期下载不受影响。

按目标机器人统一限速，当前每分钟不超过20条消息，文件和摘要均计数并预留余量。检查企微业务返回值，HTTP成功、素材上传成功、通知已排队均不能视为消息发送成功。符合附件限制时附件与摘要均需成功；超限采用链接交付时摘要成功即完成约定消息交付。接口成功不代表群成员已阅读。

### 状态与失败恢复

本机保存执行检查点、计算缓存和上传outbox，本机状态为采集中、计算中、待上传、上传中和 `uploaded_complete`。云端保存 `shops`、`agent_shop_bindings`、`runs`、`artifacts`、结构化明细与结果、规则快照及 `notification_jobs`，云端状态为 `receiving`、`incomplete`、`stored_complete`、`processing`、`notify_pending`、`delivered` 或 `delivery_unknown`。通知失败由云端记录并恢复，本机完整交接后可离线。

以云端run_id、shop_id、群配置标识、版本和消息类型识别消息，成功项不自动重复发送；摘要失败不重发已成功的附件。修订报表新建版本并注明“修订版”。通知任务持久化，云端重启或本地离线后可继续执行。

明确可重试的错误退避补发；发送超时可能已被企微接收，标记 `delivery_unknown`，核实群消息后决定是否补发。企微失败不重新抓账、计算或撤销归档文件，也不能承诺缺乏接口幂等保障时严格只发一次。

## 执行与异常恢复

建议提供以下命令，均为拟实现接口：

```text
recon inspect-template
recon collect --month 2026-08 --shop <shop_uuid>
recon import --month 2026-08 --shop <shop_uuid> --manifest <file>
recon calculate --run <run_id>
recon report --run <run_id>
recon run --month previous --all-shops
recon retry --run <run_id> --failed-only
recon upload --run <run_id>
recon upload --retry-failed
recon delivery-status --run <run_id>
```

月度任务建议使用macOS launchd。样例月汇总页面注明“每月1号10点生成上月数据”，因此建议每月1日10:30首次执行、2日补跑未完成任务；实际运行仍需验证账期已生成和笔数完整，不能只依赖固定时间。机器休眠或工作台未启动时保留待执行状态，恢复后补跑。

本项目设置运行锁，防止同一批次重复进入；平台生成报表、下载、解析和计算均保存检查点。店铺间独立记状态，单店失败继续处理其他店铺。需要登录或验证的任务保留job和已完成产物，重新登录后续跑。

本机月度任务仅恢复采集、计算、压缩及未确认上传；云端常驻服务负责完整接收后的全部流程并恢复后续任务队列，本机离线不影响云端存储、下载或企微发送。

网络超时、限流和报表生成中采用有上限的退避重试；无权限、账期不支持和字段结构变化不盲目重试。工作台重启后重读桥接配置，不复用失效令牌；恢复前查询任务状态，避免不确定的提交被重复执行。

## 实施顺序和验收

| 阶段        | 工作与交付                                         | 完成条件                                          |
| --------- | --------------------------------------------- | --------------------------------------------- |
| 1 模板与离线计算 | 提取规则、字段别名、32条映射、48条分类缺口；实现样例导入和计算             | 原始资金29896条、结算24201条、加工29900条及来源关系完整；已确定规则逐行一致 |
| 2 单店采集验证  | 用shopdesk探索财务页面；确认真实请求、主体、历史报表、下载和余额口径；形成接口样本 | 单店指定月份的各类账单可完整取得，并能识别真实无流水                    |
| 3 财务采集模块  | 实现finance异步任务、下载、截图、资源锁、断点恢复                  | 无大文件JSON回传，任务可恢复，不与其他店铺任务串主体                  |
| 4 单店端到端 | 单店归属验证、抓取计算、全量业务数据上传和云端交接 | 全量manifest通过才返回完整ACK；本机可结束；云端独立完成归档与通知 |
| 5 多店月度运行 | 统一店铺映射、多机采集、云端店铺历史查询及独立交付 | 不串店、不串主体、不重复归档或通知；本机离线后云端持续服务 |

计算验收需要逐行验证AN、AO、AP、AQ，逐项验证D2～D43、H2～H4和各账户余额。样例的外链映射、手工余额和缓存尾差需分别处理，不能为了复现旧缓存而引入隐藏补差。

代表性测试覆盖：备注同时含多个关键词；未知场景；F为空；带正负且方向为空的保证金；跨月下单但本月结算；目标月份无流水；字段增减与别名；多主体钱包；下载分片、失败和过期；登录失效；报表延迟；重复执行；余额时点错配；精确的0.01元差异。

云端交付验收覆盖：上传缺少店铺归属被拒绝；shopdesk UUID与云端shop_id不可混用；同一店铺跨机器上传归于同一店铺；未知或冲突店铺不按名称猜测；所有原始账单、截图、结构化明细及结果齐全后才返回完整ACK；缺一项不触发正式通知；本机在完整ACK后即可结束；云端根据店铺选择群；下载gzip解压后与原Excel大小及SHA-256一致；损坏文件或同键不同内容被拒绝；重复上传复用run_id且不重复通知；持久保存后才返回成功并排队通知；超过企微素材有效期后长期入口仍可用；本地离线和云端重启不丢通知；gzip超限时完整链接可用；明确失败可补传、发送超时待核实；旧版本可下载、修订版可识别；日志不泄漏凭证。

用Excel或WPS对包含非零值的代表性文件重算，验证公式语义和输出缓存。原始数据无损、自动计算与模板等价、差异结果正确以及连续月份可恢复运行均通过后，再启用常规月度任务。

实施中需先确定的业务输入是：3条缺失映射的正式归类、各账户首次期初余额、管家及保证金历史余额来源，以及未被现有汇总覆盖的非零费用如何处理。前述字段解析、模板提取和shopdesk采集封装可独立推进；这些输入未确定的账户保留待确认状态。
