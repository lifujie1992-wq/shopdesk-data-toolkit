# 抖音月度账单本地采集与整理

本机通过shopdesk复用店铺登录会话，采集账单和截图；按本目录Excel模板解析、加工、汇总，生成Excel和可独立使用的结构化源数据，并可将gzip报表推送至云端归档。企微和腾讯文档写入由后续模块接入。

## 安装

需要Python 3.11以上和uv，在项目目录运行：

```sh
uv sync --extra dev
uv run recon --help
uv run recon shops
```

`recon shops`读取正在运行的shopdesk本机桥接，不导出Cookie。不要将shopdesk UUID与平台店铺ID或云端shop_id混用。

## 先用已有账单运行

```sh
uv run recon import \
  --source 'doc/202608【抖音】Y-兹伊翰官方旗舰店-预期结果.xlsx' \
  --month 2026-08 \
  --shop-name 'Y-兹伊翰官方旗舰店' \
  --account '保证金账户=体验保证金账户'
```

此账户绑定仅用于已核实的该样例；其他账单必须填写真实账户。样例中的“店铺编码”未经核实为抖店平台ID，不直接填入 `--platform-shop-id`。支持xlsx、CSV、TSV和含这些文件的ZIP。`--source`可重复，原始文件及原列名、长编号和数据内容保留；按动账时间、结算时间等账务时间过滤加工数据。

样例运行仍可能显示“待确认”：截图不能单独证明所有账户的历史月末余额；费用分类按当前模板对照表处理，缺少映射的记录会列入异常明细。旧版32条映射曾有48条样例记录未匹配，当前用户已在模板补充三项映射。程序不用旧Excel公式缓存补齐，也不自动忽略差额。

对于分别下载的文件，推荐使用输入清单：

```sh
uv run recon import --manifest config/input.example.json \
  --month 2026-08 --shop-name '示例店铺'
```

先替换示例中的文件路径与店铺归属。月份余额可用 `--balances <json>` 提供，每项要求 `account`、`period`、`kind=monthly`、`opening`、`closing`、`source`。当前余额或OCR值不能当成历史月末余额。费用映射变更通过 `--mapping <json>` 显式传入，文件必须声明 `approved=true`；项目不默认批准候选映射。

## 千川账户（2026-10-22 新版模板）

默认采集与每月自动任务已包含 `qianchuan`。按「千川推广 → 我的资金 → 账户明细 → 流水对账 → 日结报表」查询整月，核实实际请求的广告账户 ID 和起止日期，下载官方 Excel，同时截图。枚举抖店千川入口列出的绑定账户，逐账户采集、校验并支持断点续采；不使用千川登录页的跨店账户列表。多账户时顶部主表按日汇总，每个账户的原始报表完整追加于同页下方，截图按账户依次排列，Q4/R4 为各账户月末余额之和。任一账户发生超时、下载或完整性错误仍会阻止交付；明确提示千川无权限时，按下述新规则保留本地其他来源并等待重试。

```sh
uv run recon collect --shop '<shopdesk UUID>' --month 2026-09 --kinds qianchuan
# 或直接导入已经下载的官方日结报表（可与其他 --source 一起使用）
uv run recon import --source '/absolute/path/财务流水.xlsx' --month 2026-09 --shop-name '店铺名'
```

工作表按当前模板的原顺序保留，兼容8、9、10页模板。千川日结报表按模板 A:N 写入，明细截图嵌入同页 P8 右侧区域；Q3/R3 为余额标题，Q4/R4 按目标月份最后一个自然日提取赠款/非赠款余额，不依赖报表排序。下载原件、截图及结构化数据一并保留。模板本身的示例流水、截图与 Q4/R4 示例数值不会被用作采集结果。

「核对汇总」D44/D45 保留模板公式原文和数组公式属性，N6/O6/P6 保留原公式，M6 仅使用已核实的千川月度期初余额，未知时留空，不使用模板示例余额。D44 = 非赠款消耗转负，D45 = 总存入减赠款消耗，严格遵循模板。缺列、重复日期、账期错误、明细与总计不符或有明细但缺少截图会提示待确认。空报表截图仅保留为原始采集凭证，不嵌入千川账户 sheet；页内只展示有明细数据的截图。

整月没有数据、只有部分日期有数据、月末当天没有记录均为正常情况，无需用户补数据、补权限或确认业务范围。资金／结算月汇总会核查完整列表（包含翻页），目标月份没有账单行或笔数为0时记录 `no_activity`，不再等待不存在的行或执行空导出；保证金表格的“暂无数据”占位行不算交易。加载失败、权限提示及列表未查全仍保留错误，不会伪装成无数据。全部来源无数据时仍生成报表并完成采集，不因没有下载文件而重试。

千川按官方实际日期保留明细，不补齐无记录的日期；总计仍须与实际明细相符，正式下载的明细条数仍须匹配同月、同账户的官方查询条数。查询无数据时模板总计为0，但历史余额不填0。缺少月末当日记录时保留金额及正常采集状态，Q4/R4用 `#N/A` 表示余额无记录，旁边注明原因，保留原核对公式；该标记不是采集异常。多账户中任一账户月末余额无记录时，不将其余额当作0合计。无数据不产生用户待办；正常采集与财务余额核对是否具有完整依据分别记录。

2026-10-25 最新确认：保留 `success_data`、`success_empty`、`failed` 三种千川获取状态。明确无访问权限仍属于 `failed`，但允许其他有效账户先上传，报表整体为 `pending`；D44/D45、千川发生额及余额留空，不合成零总计，不标记全部费用完整。超时、下载失败、数据不完整，以及其他来源或公式缓存异常仍阻止上传。此确认覆盖当天说明文档中“无权限阻止整单上传”的要求。只有完整月份、同广告账户的官方成功空查询（或有明确官方未开通依据）才能生成零发生额总计；表头空文件本身不是无发生依据。未知余额不补0。不新增工作表和上传API字段。

最终 Excel 保存后重新检查费用名称、全部费用金额、D44/D45、N6 与 H2/H3/H4 数值缓存、原公式及数组属性。按名称定位千川费用行，完整查询条数与明细一致时允许生成缺失的唯一总计，多账户原报表保留在同页下方B:O，主表A列仅有一个“总计”。明确无权限时仅豁免千川缺失，反而禁止该账户填写0或旧金额，其他账户和H2/H3/H4仍严格校验。部分有效报表的本地校验结果为 `ready=true, complete=false, expense_status=partial`，其余费用校验失败不生成gzip；余额缺失单独记录。通过校验后才计算最终Excel哈希、gzip及其哈希并冻结上传身份；新产物使用新运行ID，网络重试仍复用原产物。

## 实时采集

```sh
uv run recon collect --shop '<shopdesk UUID>' --month 2026-09
# 开发联调时只采两种报表
uv run recon collect --shop '<shopdesk UUID>' --month 2026-09 --kinds fund,settlement
# 复用已成功下载的文件、主体结果，只重试未完成项目
uv run recon collect --shop '<shopdesk UUID>' --month 2026-09 \
  --resume 'data/runs/collection-<采集批次>/collection.json'
```

采集器通过官方页面控件生成报表，并由shopdesk下载扩展保存文件。资金、结算按月份定位，按报表ID核实账期、类型和店铺；涉税账单枚举主体并验证实际查询的member_id和月份。保证金导出完整历史流水（清单标记 `export_scope=all_history`），原表完整保留，计算层只取目标月份。截图保留原图与采集时点，当前余额不能冒充历史月末余额。不同账号的页面或权限有差异：无法核实账户、主体或报表归属时明确记录失败，不把失败当无流水。

下载和截图需安装本项目的shopdesk扩展：

```sh

uv run python tools/install_shopdesk_extension.py
# 在工作台空闲并且方便重启时安装
uv run python tools/install_shopdesk_extension.py --install
```

安装器检查业务任务状态，保留原archive和Info.plist备份，默认使用macOS正常退出；系统取消退出或应用未退出时停止。仅在桥接确实无响应、持久化业务任务为空、进程身份核实一致时，可显式加 `--recover-unresponsive` 恢复卡死进程。补丁只修改当前已部署archive中的探索扩展，不运行工作台原有的整体部署脚本。源码与扩展测试位于 `shopdesk/` 和 `tests/test_shopdesk_extension.cjs`。现有app升级可能覆盖该扩展，需要重新检查安装。

## 每月全店自动运行

Mac 定时任务为 `local.douyin-settle-recon.monthly`，每月 **1日01:00（北京时间）**&#x5F00;始处理上个月账单。例如2026-11-01处理2026-10，2027-01-01处理2026-12。每批从工作台实时读取全部抖店登录记录，顺序采集资金、结算、两类保证金、管家账户、涉税账单和千川账户，生成Excel/gzip并复用发票客户端凭据逐店推送。相同店名不直接合并，取得已验证的平台店铺ID后才去重。

```sh
# 注册/更新本机定时任务；不立即触发全店采集
uv run recon schedule --install
uv run recon schedule

# 只查看当前店铺及账期计划，不下载、不推送、不创建批次
uv run recon monthly --dry-run

# 人工运行指定月份；不指定--month时使用北京时间的上个月
uv run recon monthly --month 2026-10

# 修复登录/权限/配置后，立即恢复该月份采集失败或达到失败上限的店铺
uv run recon monthly --month 2026-10 --retry-failed
```

首次安装于2026-10-19，首个计划时间为 **2026-11-01 01:00**，处理10月；不会在安装时自动补跑9月。LaunchAgent注册在 `~/Library/LaunchAgents/local.douyin-settle-recon.monthly.plist`；每小时也会唤起一次，仅续跑已到期的批次和待重试任务。没有到期批次时直接退出，不会每小时重新采集。Mac休眠/关闭或工作台未就绪时保留原计划游标，恢复后继续处理应跑的月份；Mac需开机且登录当前用户，工作台需运行并保有有效店铺登录。

## 云端报表数据同步接口

上传器按照[Mac 对接文档](doc/mac-douyin-recon-upload.md)及[OpenAPI 1.4.0](doc/mac-douyin-recon-upload.openapi.json)实现，每次 POST `/api/douyin-recon/v1/reports`，只传 `metadata` 与一个 `.xlsx.gz` 附件。metadata 新增 `platform: "douyin"`，契约另定义 `taobao` 和 `xiaohongshu`；按 `(platform, shop_id)` 唯一识别店铺，名称保持平台原名，不添加 `Y-`。云端需先同步支持新字段的接收、存储、唯一校验和 GET 回传，再部署此版本上传器。使用macOS自带curl流式发送，客户端库生成multipart边界；凭据通过进程标准输入交给curl，不放入命令参数、业务日志、任务或回执。

默认直接读取 Mac 发票客户端的 `~/.config/invoice-mac-agent/config.json`，复用 `workbenchBaseUrl`、`accountId`、`workerToken`，不复制Token或修改该客户端配置；同样支持其 `INVOICE_AGENT_WORKBENCH_BASE_URL`、`INVOICE_AGENT_ACCOUNT_ID`、`INVOICE_AGENT_WORKER_TOKEN` 环境变量。覆盖优先级为本项目环境变量 `RECON_API_BASE` / `INVOICE_ACCOUNT_ID` / `INVOICE_WORKER_TOKEN`、显式 `--upload-config`、发票客户端环境变量、发票客户端配置。站点未配置时默认 `https://erp.xiangduoer.com`，必须是站点根地址。另有独立[配置示例](config/upload.example.json)，私有配置可保存为被git忽略的 `config/upload.local.json`。

```sh
# 先检查现有9月结果的身份、日期、月份、文件完整性及上传metadata，不访问网络
uv run recon upload --run data/runs/20261019T091450Z-18744767 --dry-run

# 复用本机发票客户端配置上传已有结果；--run可重复，逐份串行上传
uv run recon upload --run data/runs/20261019T091450Z-18744767

# 以后采集完成后直接上传，不必重新读取或计算报表
uv run recon collect --shop '<ShopDesk UUID>' --month 2026-09 \
  --platform-shop-id '<已核实的抖店ID>' --upload

# 查看任务；只重试已到期的任务；等待并执行最多4次退避尝试
uv run recon upload-status
uv run recon upload-queue
uv run recon upload-queue --watch

# 401/409等需先修正配置；人工恢复失败任务时仍使用原运行ID和原metadata
uv run recon upload-queue --retry-failed
```

`recon import`也支持 `--upload`。本地生成成功后上传失败会保留报表和任务，并返回退出码3；用上传命令继续，不要为网络重传重新采集。`--prepare-only`只冻结任务不发送，需账号ID但不需Token。上传失败不会删除其他成功任务或本地Excel/gzip。

日期按已确认规则分开记录：`reconciliation_date`是原运行的北京时间执行日期，`reconciliation_month`是抓取核对的账单月份；10月19日处理9月即 `2026-10-19` / `2026-09`。新产物在manifest保存执行日期；旧产物读取原 `result.json` 或 `tables.json` 的运行时间并换算北京时间，从不使用重试日期或文件修改时间。缺少原执行时间时，必须通过 `--reconciliation-date YYYY-MM-DD` 指明。

采集开始和结束时，从新打开的抖店官方页面读取平台提供的最新店铺 ID、名称；只将这两个字段带回本地，不读取或输出该页面身份对象中的凭据。每次新运行首次进入上传队列前，再使用该店的 ShopDesk 独立登录会话刷新平台身份。`shop_id` 必须等于已核实的 `platform_shop_id`，工作台旧标签、手动 `--shop-name`、历史报表名称不会覆盖平台店名；手动 `--shop-id`／`--cloud-shop-id` 与平台 ID 不一致时拒绝入队，不会改绑其他店铺。纯本地导入要上传时，也必须提供 `--shop` 以核实最新平台身份；`--dry-run` 只检查本地资料，不联网刷新。入队后冻结平台、ID、名称，网络重试沿用原请求；后续改名由新运行更新，不改写历史已上传报表。

任务保存在 `data/upload-queue/tasks/<运行ID哈希>/`：`metadata.json`是不可修改的业务快照，`shop-identity.json`保留首次入队前的平台身份核实时间和来源，`task.json`记录账号、目标站点、状态和尝试次数，`receipt.json`保存已验证的归档回执和按站点根地址解析的下载链接。队列锁和账号锁保证串行。重试复用运行ID、原业务日期、原文件及原metadata；旧队列不强行增加 `platform` 或刷新名称，同一任务不能换账号或站点。Token可以在同一账号下更新。

仅在HTTP 200/201、`code=OK`、`stored`严格为true、非空report_id、运行ID及Excel哈希全部匹配时标记 `uploaded`，并验证duplicate与下载地址格式；200幂等回执同样成功。429遵守 `Retry-After`；网络错误、无法确认的成功回执和500/502/503/504按30秒、2分钟、10分钟加少量抖动排期，最多4次。普通命令尝试一次后将排期写盘，`upload-queue --watch`持续执行到成功或达到上限；400/401/404/405/409/413/415/422直接保留失败等待处理。`stored=true`只表示归档成功，账单仍可能是pending或different。

## 后续腾讯文档源数据接口

不用重新读取Excel，直接分页导出某表的有序单元格和row_id：

```sh
uv run recon export-grid --run 'data/runs/<run_id>' \
  --table processed_funds --offset 0 --limit 500 \
  --output 'data/grid-page.json'
```

结果包含 `columns`、`rows[].values`、`rows[].row_id`、`rows[].source`、`total`和`next_offset`。`values`严格遵循columns顺序，可由未来腾讯文档适配器映射到目标表格接口。十进制金额保持字符串精度，真实写入时根据目标API的单元格类型转换；长编号必须按文本写入。截图独立引用原图，不能用本地路径直接填入在线图片单元格，后续需上传图片并保存云端资源映射。
