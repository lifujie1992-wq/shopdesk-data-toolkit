# 抖店自动申诉 · 流程说明

> 最后更新：2026-10-08（按当时实际运行的代码/定时任务整理）

---

## 一、一句话总览

**每天早上 6:35，Mac 自动把所有店铺近 30 天的「中差评」和「品退」扫一遍，AI 判断哪些能申诉，能自动报的直接报，拿不准的丢进「核对队列」；你在云端页面上点确认，Mac 每 30 分钟把确认的单子真正提交到抖店。**

---

## 二、四个组成部分

| 部分            | 在哪                             | 干什么                                           |
| ------------- | ------------------------------ | --------------------------------------------- |
| **① 工作台 App** | Mac 上 `~/店铺工作台.app`            | 真正干活的人。存着 40 家店的登录态，负责采集数据、读飞鸽聊天、调 AI 判断、提交申诉 |
| **② 本地页面**    | Mac 上 `http://127.0.0.1:8899/` | 你自己在 Mac 上看数据/调试用                             |
| **③ 云端页面**    | `erp.xiangduoer.com/appeal/`   | **客服/你在外面用的**。看工单、核对、点「确认」                    |
| **④ 云端服务器**   | `root@47.114.33.246`           | 存云端页面 + 数据（`/srv/appeal-workbench/`）          |

**核心分工**：

- **云端 = 看 + 确认**（人在外面也能操作）
- **Mac = 执行**（因为提交申诉需要店铺登录态，只有 Mac 有）

## 三、一次完整流程（从数据到提交）

```
┌─ ① 采集（Mac）───────────────────────────────────────┐
│  品退    ：拉「申请原因=商品品质原因」的全部售后       │
│  中差评  ：拉 1~3 星评价里"内容为空或纯情绪+无图"的     │
│  → 产出 worklist 工单文件 + 全量池文件                │
└──────────────────────────────────────────────────┘
                        ↓
┌─ ② 筛查候选（Mac）───────────────────────────────────┐
│  去掉：平台终态（不可举报/无需举报/已举报过）          │
│  剩下的 = 候选（candidates）                          │
└──────────────────────────────────────────────────┘
                        ↓
┌─ ③ 逐单判断（Mac，最慢的一步）───────────────────────┐
│  对每一单：                                          │
│   a. 打开飞鸽聊天 → 看买家有没有说话/发图/客服回复      │
│   b. 调 AI → 判断这单该不该报、用什么理由、写申诉文案   │
│   c. 平台预审 → 查这单还能不能报（can_select）         │
│   d. 决定：自动提交 / 入核对队列 / 跳过                │
└──────────────────────────────────────────────────┘
                        ↓
        ┌───────────────┴───────────────┐
        ↓                               ↓
┌─ ④a 自动提交 ─────┐        ┌─ ④b 入核对队列 ──────────┐
│ 条件：             │        │ 拿不准的都进这里          │
│ • 平台预审 = high │        │ 状态：待核对              │
│ • 或历史通过率≥70%│        │ → 等人工确认              │
│  且样本≥20        │        └──────────────────────────┘
└──────────────────┘                         ↓
                        ┌────────────────────┘
                        ↓
┌─ ⑤ 人工确认（云端页面）──────────────────────────────┐
│  你在 erp.xiangduoer.com/appeal/ 上：                 │
│   • 看 AI 写的申诉文案，可改                          │
│   • 点「确认」→ 写入云端 confirmations.jsonl          │
│   • 也可「不举报」                                    │
└──────────────────────────────────────────────────┘
                        ↓
┌─ ⑥ 回传 + 提交（Mac，每 30 分钟）────────────────────┐
│  submit-confirmed.sh：                                │
│   ① 拉云端确认（confirmations.jsonl）→ 合并进本地队列  │
│   ② 把 data/stats/queue 推回云端（让你看到最新）       │
│   ③ 调 App 以「confirmedOnly」模式提交 → 真正报到抖店 │
└──────────────────────────────────────────────────┘
                        ↓
┌─ ⑦ 回访结果（Mac，每天的那轮顺带做）─────────────────┐
│  同步平台举报记录（约 880 单）→ 更新每单审核状态：      │
│   举报成功 / 举报失败 / 审核中                        │
└──────────────────────────────────────────────────┘
```

## 四、定时任务（谁在什么时候跑）

| 时间               | 任务                             | 干什么                                  | 脚本                    |
| ---------------- | ------------------------------ | ------------------------------------ | --------------------- |
| **每天 06:35**     | `local.shopdesk.appeal`        | **主流程**：跑一轮完整申诉（采集→判断→入队/自动提交）       | `daily-appeal.sh`     |
| **每 30 分钟**      | `local.shopdesk.appeal-submit` | 拉云端确认 + 推送数据 + 提交已确认的单               | `submit-confirmed.sh` |
| **每 5 分钟**       | `local.shopdesk.autodeploy`    | 检查 github 有没有新代码 → 有就自动更新+重建（跑批中会跳过） | `autodeploy.sh`       |
| **每天 9/13/17 点** | `local.shopdesk.health`        | 查 40 家店的登录状态 + 飞鸽权限，异常发飞书告警          | `health-check.sh`     |

**注意**：`autodeploy` 会把本地代码 **强制重置成 github 上的**（`git reset --hard origin/main`）。  
所以**改了代码必须先 push 到 github**，否则 5 分钟后会被覆盖掉。

## 五、状态字典

### 工单状态（页面上每一单的状态）

| 状态       | 含义                      |
| -------- | ----------------------- |
| **待核对**  | AI 判断需要人看，等你确认          |
| **已确认**  | 你确认了，等 Mac 提交           |
| **审核中**  | 已提交平台，等结果               |
| **举报成功** | 平台通过（差评率/品退率已剔除）        |
| **举报失败** | 平台驳回                    |
| **不可举报** | 平台判定不能报（含"无需举报"），放弃     |
| **不可申诉** | 品退全量池专用：不符合申诉条件，已自动排除   |
| **未核查**  | 品退全量池专用：本批超出逐单核查上限，暂未判定 |
| **未处理**  | 系统还没处理过                 |

### 跳过原因（为什么不报）

| 原因          | 含义                       |
| ----------- | ------------------------ |
| 不可举报 / 无需举报 | 平台判定不能报 ← **终态，不再重试**    |
| 已举报过        | 该单已有举报记录（平台一单一报）← **终态** |
| 需人工介入·判断不确定 | AI 拿不准 → 现在会入核对队列        |
| 需卖家提供质量证明   | 聊天里有图片证据，要准备材料           |
| 买家反馈真实问题    | 买家指出了具体缺陷，不宜举报           |
| 买家发过图片      | 买家发过图片/视频证据              |
| 买家有沟通       | 买家和客服聊过，需人工看             |
| **飞鸽未加载**   | 页面没加载成功 ← **临时，会自动重试**   |
| **飞鸽无会话权限** | 子账号缺权限 ← **临时，开通后自动重试**  |
| **飞鸽登录失效**  | 店铺登录掉了 ← **临时，重登后重试**    |

> **重要**：只有前三个（不可举报/无需举报/已举报过）是**永久排除**的。  
> 其他（尤其飞鸽相关的）都是**临时失败，下次跑批会自动重试**。  
> （这个坑 2026-10-07 修过：以前所有跳过都当终态，导致失败一次就永久拉黑。）

## 七、为什么会有"补跑"？（你问的那个）

**正常情况**：每天 06:35 那一轮就够了 —— 采新的、报新的、回访老的。

**需要补跑的情况**（都是 bug 或配置问题，不是日常）：

| 情况         | 原因                          | 现状                                                |
| ---------- | --------------------------- | ------------------------------------------------- |
| 品退一直跑不出来   | 采集口径不对（翻 1000 条售后碰运气）       | ✅ 2026-10-07 修好，改成平台精确口径 `reason=product_quality` |
| 失败的单不重试    | 跳过名单全当终态了                   | ✅ 已修，只有平台终态才排除                                    |
| 品退确认提交不出去  | 提交语句只写了 `kinds:["reviews"]` | ✅ 已修，加了 `quality`                                 |
| 品退池一堆"未核查" | 单次逐单核查上限 600，大店超了           | ✅ 已提到 2200，跑完清零                                   |

**结论**：这些修完之后，**理论上不需要天天补跑了** —— 每天 6:35 那轮 + 30 分钟提交就够了。  
如果某天还要补跑，说明又出了新 bug，应该去修 bug 而不是补跑。

## 八、手动操作速查

```bash
# 看 App 接口端口/token
plutil -extract port raw -o - ~/Library/Application\ Support/shopdesk/agent-bridge.json

# 手动跑一轮申诉（品退+中差评，36 家白名单）
#   kinds: quality=品退, reviews=中差评
curl --config - -s -H 'Content-Type: application/json' \
  -d '{"method":"auto_appeal_start","args":{"kinds":["quality","reviews"],"submit":true,"reviewQueue":true}}' \
  http://127.0.0.1:$PORT/call

# 看跑批进度
curl ... -d '{"method":"auto_appeal_status"}' http://127.0.0.1:$PORT/call

# 单跑某个采集器
curl ... -d '{"method":"start_collector","args":{"key":"builtin:quality_returns"}}' ...

# 手动同步云端（拉确认+推数据）
bash ~/shopdesk-workbench-src/tools/sync-appeal-cloud.sh

# 手动提交已确认的单
bash ~/shopdesk-workbench-src/tools/submit-confirmed.sh

# 改完代码必须（否则 5 分钟后被 autodeploy 覆盖）
cd ~/shopdesk-workbench-src && git add -A && git commit -m "..." && git push origin main
FORCE=1 bash build.sh        # 跑批中会中止，用 FORCE=1 强行（但会中断跑批！）
```

> ⚠️ **跑批进行中不要 `build.sh`** —— 它会重启 App，把跑批打断。  
> `autodeploy` 已经做了保护（跑批中跳过），手动执行要自己注意。

## 九、本地页面 vs 云端页面

两边**不是同一个文件**（云端多了收藏、`/appeal/api/*` 接口等），但**展示逻辑要保持一致**：

**改页面时两边都要改**：

1. 本地：`src/appeal-web.js`（HTML 在模板字符串里，**正则里的反斜杠要写两个** `\d` → `\\d`）
2. 云端：`/srv/appeal-workbench/index.html`（普通文件，无反斜杠问题）

改完本地 `build.sh`，云端 `scp` 上去。

## 十、加新筛选/新能力时

**平台的筛选参数是英文字符串编码**（踩过坑：不是数字）：

```
after_sale/pc/list 的 body：
  reason           = product_quality    → 申请原因=商品品质原因
  after_sale_type  = presale_all        → 未发货退款
  其他：appeal_todo(待申诉) / return_receive(待商家收货) / shop_refund(商家同意退款)
```

**怎么挖新编码**：用 App 的 `flyge_probe` 打开抖店页面 → 点「展开更多筛选」→ 打开对应下拉 → 读 `[role=option]` 元素的 `aria-label`（标签）和 `innerText`（值）。
